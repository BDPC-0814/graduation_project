# 面向故障演化的异构算力设备多维风险自适应变频采样系统设计书

## 一、系统名称

面向故障演化的异构算力设备多维风险自适应变频采样系统。

## 二、文档定位

本文档用于说明本系统的总体设计方案、核心算法、功能组成与使用方式。文档写法参考技术交底材料的组织方式，但内容定位为系统设计书，重点面向系统实现、功能落地和实验使用。

## 三、技术领域

本系统属于异构算力设备运行状态监测与边端智能采样领域，具体涉及一种面向 CPU、GPU、NPU 等设备的多维风险自适应变频采样方法，以及配套的边端可靠执行、远端接收、可视化分析和实验评估系统。

## 四、背景与问题

在异构算力设备监测场景中，若长期使用固定频率全字段采样，会带来以下问题：

1. 平稳阶段采样开销高，大量样本对状态判定贡献有限。
2. 异常演化阶段响应不够快，容易错过突发负载、热压力或错误状态形成前后的关键窗口。
3. CPU、GPU、NPU 的采集接口和字段并不一致，难以形成统一采样和统一分析链路。
4. 边端设备存在本地缓存、写盘、网络波动、上传失败重试等现实问题，单纯设计“调频算法”无法保证系统可用性。
5. 扩展字段全部高频采集会放大性能开销，但如果全部低频采集，又会损失诊断细节。

因此，本系统将问题重新定义为：

**在异构算力设备故障演化过程中，如何在保证关键状态及时感知的前提下，降低无效采样和执行开销，并通过边端可靠执行链路保证数据最终可达。**

## 五、设计目标

本系统的设计目标包括：

1. 建立面向故障演化过程的多维风险自适应采样机制。
2. 在设备平稳阶段主动拉长采样间隔，在异常阶段快速进入高频聚焦采样。
3. 以“字段分层采样”替代“全字段固定频率采样”，将快线字段与慢线字段分开调度。
4. 将边端缓存、WAL 持久化、失败重试和上传背压纳入算法决策过程。
5. 形成一套从边端采集到后端展示再到实验评估的完整系统。
6. 支持实时采集模式和可复现实验回放模式。

## 六、总体技术方案

### 6.1 总体思路

本系统采用“设备适配层 + 分层采样层 + 相位调度层 + 边端执行层 + 后端服务层 + 前端展示层 + 实验评估层”的总体结构。

系统运行时，先由不同设备适配器采集快线状态，再由调度器根据设备演化紧迫度、字段刷新优先级、边端执行压力三类控制量决定：

1. 下一轮采样间隔。
2. 当前采样相位。
3. 是否触发慢线字段补采。
4. 当前采用直传、缓冲上传还是降级缓存。

### 6.2 总体架构

系统可分为以下六个功能层：

1. 设备采集层  
   面向 CPU、GPU、NPU 和回放轨迹提供统一采集接口。

2. 分层采样层  
   将采集字段分成快线字段与慢线字段，优先用快线字段做快速判断，再按需补采慢线字段。

3. 调度决策层  
   根据三类控制量选择采样相位、字段策略、传输策略和下一轮间隔。

4. 边端执行层  
   通过环形缓冲区、SQLite WAL outbox、后台上传线程完成可靠落盘和异步传输。

5. 后端服务层  
   提供接收、入库、查询、历史对比、日志和实验结果查询接口。

6. 展示与评估层  
   提供前端可视化页面和固定频率/故障演化采样的对照实验评估能力。

## 七、核心算法设计

## 7.1 问题定义

本系统将采样问题定义为：

**面向故障演化的多维风险自适应变频采样。**

这里的“故障演化”不是指设备已经彻底失效，而是指设备从平稳状态逐步进入负载升高、热压力累积、功耗异常、限频、错误告警或采集异常等状态变化过程。算法的目标不是简单“降采样”，而是在不同演化阶段动态调整采样强度和采样内容。

## 7.2 三类控制量

系统不再沿用旧的四分量风险框架，而采用三类新的控制量：

### 7.2.1 紧迫度 `urgency_score`

用于表示当前设备状态是否正处于故障演化的关键阶段，主要由以下因素共同构成：

1. 当前利用率水平。
2. 相对历史基线的上升幅度。
3. 相邻两次采样的突变量。
4. 温度接近热阈值的程度。
5. 功耗接近功率上限的程度。
6. 限频标志、错误标志和异常状态。

该量越高，说明设备越可能处于需要快速观察和细粒度跟踪的阶段。

### 7.2.2 字段优先级 `field_priority_score`

用于表示当前是否有必要刷新慢线字段，主要考虑：

1. 慢线字段距离上次补采已经过了多少轮。
2. 快线字段是否出现明显波动。
3. 利用率、温度、功耗是否相对基线发生漂移。
4. 是否出现限频、错误或异常标志。

该量越高，说明当前应尽快补采 ECC、PCIe、线程、缓存、设备状态等慢线字段。

### 7.2.3 执行压力 `execution_pressure_score`

用于表示边端执行链路当前承受的压力，主要由以下因素构成：

1. SQLite outbox 中待发送记录数量。
2. 死信记录数量。
3. 环形缓冲区积压比例。
4. 上传器是否在线、是否存在持续回压。

该量越高，说明即使设备本身有监测需求，也需要考虑边端系统的承载能力，避免采样与上传链路失控。

## 7.3 相位驱动控制器

本系统采用相位驱动控制器，而不是简单的“风险数值映射到频率”的闭环结构。调度器每一轮根据三类控制量选择以下相位之一：

1. `聚焦采样`
   适用于故障演化明显、状态突变或设备异常阶段，采样间隔压缩到最小值附近，通常同时触发慢线补采。

2. `恢复观测`
   适用于从高风险回落但仍需持续观察的阶段，采样频率高于巡航阶段，慢线字段按需分层补采。

3. `巡航巡检`
   适用于状态平稳阶段，采样间隔可以逐步拉长，以降低无效开销。

4. `边端降级`
   适用于边端积压过高、上传受阻或缓冲压力显著升高的阶段，系统优先保证关键快线字段和本地可靠缓存。

## 7.4 字段分层采样机制

字段分层采样是本系统的主创新点之一。

### 7.4.1 快线字段

快线字段用于高频快速判断，典型包括：

1. `utilization`
2. `chip_temp_c`
3. `power_w`
4. `mem_util_percent`
5. `status`
6. `error`
7. `last_error_code`
8. `throttle_flag`

这些字段采集代价相对较低，且对状态演化判断最敏感。

### 7.4.2 慢线字段

慢线字段用于补充诊断信息，典型包括：

1. `freq_mhz`、`freq_cap_mhz`
2. `pcie_rx_MBps`、`pcie_tx_MBps`
3. `power_limit_w`
4. `fan_rpm`
5. `nv_throttle_reasons`
6. `nv_ecc_correctable_total`、`nv_ecc_ue_total`
7. `threads`
8. `ctx_switch_rate`
9. `l3_cache_mib`
10. `io_util_percent`

这些字段不再默认每轮采集，而是在聚焦、恢复或巡航补采条件满足时再刷新。

### 7.4.3 分层采样流程

单设备一次调度流程如下：

1. 先采集快线字段。
2. 基于快线字段计算三类控制量。
3. 调度器输出当前相位、字段策略、传输策略和下一轮间隔。
4. 若当前相位或字段优先级要求补采，则采集慢线字段。
5. 将快线和慢线合并为统一指标记录。
6. 交由边端执行链路完成缓冲、写盘和上传。

## 7.5 边端可靠执行链路作为算法组成部分

本系统将边端可靠执行链路明确纳入算法，而不是作为调度器之外的附属功能。

边端执行链路由以下部分组成：

1. `RingBuffer`
   用于吸收短时采样输出峰值，避免主采样线程因写盘阻塞。

2. `SQLiteOutbox`
   使用 SQLite WAL 持久化待发送记录，保证程序退出、网络抖动或接口失败后数据仍可重试。

3. `HTTPUploader`
   支持 gzip 压缩批量上传，提升远端接收效率。

4. 后台 WAL 线程与上传线程
   采样主线程不直接执行阻塞式上传，而是交由后台线程处理，提高整体稳定性。

5. 死信控制
   上传连续失败超过阈值后进入 `dead` 状态，避免无限重试拖垮系统。

换言之，本系统不是单纯输出“下一个采样间隔”的算法，而是输出“采样内容 + 采样频率 + 传输方式 + 边端容错策略”的联合决策。

## 7.6 算法输出

每轮调度至少输出以下结果：

1. `interval`
   下一轮采样间隔。

2. `phase`
   当前采样相位。

3. `field_policy`
   当前字段采样策略，如快线必采、分层补采、全量聚焦、降级保活等。

4. `transport_policy`
   当前传输策略，如直传、缓冲上传、降级缓冲、本地缓存等。

5. `sampled_slow`
   本轮是否触发了慢线补采。

6. `evolution_score`
   当前演化分数，用于前端展示和实验评估。

## 八、系统功能详细说明

## 8.1 设备适配功能

系统当前支持以下设备来源：

1. CPU 适配器
   基于 `psutil` 和平台能力采集 CPU 利用率、频率、线程、上下文切换、I/O 利用率等字段。

2. GPU 适配器
   优先走 NVIDIA NVML，Windows 下可兼容通用 GPU 信息探测；支持温度、功耗、显存占用、频率、限频原因等字段。

3. NPU 适配器
   基于 `npu-smi info` 解析 NPU 状态信息。

4. Replay 适配器
   从标准轨迹 CSV 回放设备状态，用于可复现实验。

## 8.2 统一指标模型功能

系统通过统一指标模型封装异构设备的快线和慢线字段，使 CPU、GPU、NPU 在后续调度、入库、展示和评估阶段具备统一的数据结构。

统一模型具备以下特点：

1. 静态信息与动态信息分离。
2. 通用字段与设备特有字段并存。
3. 缺失的真实温度或功耗保持为空，不用伪造数值。
4. 支持兼容字段回填，便于现有链路接入。

## 8.3 单设备采样功能

单设备采样器负责完成以下工作：

1. 调用设备适配器采集快线字段。
2. 获取调度决策。
3. 判断是否触发慢线补采。
4. 将快线数据和慢线数据合并。
5. 形成完整的单设备采样记录。

## 8.4 多设备边端编排功能

边端代理 `EdgeAgent` 负责管理多个设备的采样执行。其主要功能为：

1. 为每个设备维护独立的下一次到期时间，避免所有设备被绑在同一个固定节拍上。
2. 并发触发多设备采样。
3. 将运行时反馈注入每个设备调度器。
4. 将采样记录送入环形缓冲区。
5. 在后台完成 WAL 落盘和异步上传。

该设计适合异构设备场景，因为不同设备的最优采样间隔不相同，必须允许设备按各自节奏运行。

## 8.5 后端接收与查询功能

后端服务基于 FastAPI 实现，主要功能包括：

1. 接收边端上传的批量指标与事件。
2. 将指标与事件写入数据库。
3. 提供设备列表、实时指标、历史曲线、日志、事件查询接口。
4. 提供实验评估报告接口。
5. 提供调度器配置和概览统计接口。

## 8.6 前端展示功能

前端页面用于展示：

1. 实时设备快照。
2. 利用率、演化分数和采样间隔趋势。
3. 最近日志与事件。
4. 固定频率与故障演化采样的离线评估结果。

前端显示与后端字段保持一致，主要围绕 `evolution_score`、`phase`、`field_policy`、`transport_policy` 等新术语展开。

## 8.7 可复现实验功能

系统支持生成标准回放轨迹，并在同一条轨迹上分别运行固定频率模式和故障演化采样模式。该功能可用于：

1. 消除实时机器波动对实验结论的干扰。
2. 让不同参数配置之间具有可比性。
3. 利用 ground-truth 事件表统一评估响应延迟。

## 十、使用说明

## 10.1 环境准备

建议使用项目根目录下的虚拟环境，并保证前后端依赖已经安装完成。

项目根目录下主要运行入口包括：

1. `demo/evolution_sampling_experiment.py`
2. `demo/generate_replay_trace.py`
3. `demo/evaluate_metrics.py`
4. `demo/run_midterm_check.ps1`

## 10.2 启动后端

在项目根目录执行：

```powershell
python -m uvicorn backend.app.main:app --reload --port 8001
```

启动后可通过 `http://127.0.0.1:8001/health` 检查后端状态。

## 10.3 启动前端

```powershell
cd frontend
npm run dev
```

前端默认用于查看设备实时快照、历史曲线、事件和实验评估结果。

## 10.4 实时采集模式

若需要直接采集本机 CPU/GPU/NPU 状态，可不传 `--trace-file`，例如：

```powershell
python demo\evolution_sampling_experiment.py --mode evolution --device cpu,gpu --vendor intel --duration 60 --output experiments\evaluation\latest\live_evolution.csv --event-output experiments\evaluation\latest\live_evolution_events.csv --outbox-db experiments\evaluation\latest\live_evolution.db --remote-endpoint http://127.0.0.1:8001/api/ingest
```

说明如下：

1. `--mode evolution` 表示使用故障演化采样模式。
2. `--device cpu,gpu` 表示启用 CPU 和 GPU。
3. `--vendor intel` 用于指定 GPU 厂商探测偏好。
4. `--remote-endpoint` 表示边端结果会同时上传到后端。

## 10.5 可复现实验模式

先生成标准回放轨迹：

```powershell
python demo\generate_replay_trace.py
```

再在同一条轨迹上分别运行 fixed 与 evolution：

```powershell
python demo\evolution_sampling_experiment.py --mode fixed --device all --trace-file experiments\replay_profiles\heterogeneous_fault_trace.csv --duration 85 --output experiments\evaluation\latest\replay_fixed.csv --event-output experiments\evaluation\latest\replay_fixed_events.csv --outbox-db experiments\evaluation\latest\replay_fixed.db
```

```powershell
python demo\evolution_sampling_experiment.py --mode evolution --device all --trace-file experiments\replay_profiles\heterogeneous_fault_trace.csv --duration 85 --output experiments\evaluation\latest\replay_evolution.csv --event-output experiments\evaluation\latest\replay_evolution_events.csv --outbox-db experiments\evaluation\latest\replay_evolution.db
```

注意：

1. 只要传入 `--trace-file`，系统就进入回放模式，不再读取本机实时硬件数据。
2. 回放模式用于公平对照实验，不用于反映真实机器当下状态。

## 10.6 实验评估

```powershell
python demo\evaluate_metrics.py --fixed experiments\evaluation\latest\replay_fixed.csv --evolution experiments\evaluation\latest\replay_evolution.csv --ground-truth-events experiments\replay_profiles\heterogeneous_fault_events.csv --output-dir experiments\evaluation\latest
```

该命令会输出评估报告，主要指标包括：

1. 采样点数量。
2. 冗余率。
3. 平均采样间隔。
4. 响应延迟分布。
5. 慢线激活率。
6. 缓冲上传占比。
7. 聚焦相位占比。
8. 平均执行压力。

## 10.7 一键运行方式

如需一键完成前后端启动、fixed/evolution 实验和评估，可执行：

```powershell
powershell -ExecutionPolicy Bypass -File demo\run_midterm_check.ps1 -Devices all -ReplayTrace experiments\replay_profiles\heterogeneous_fault_trace.csv -GroundTruthEvents experiments\replay_profiles\heterogeneous_fault_events.csv -Duration 85
```

## 十一、系统特点与优势

与传统固定频率全字段采样方式相比，本系统具有以下特点：

1. 采样决策不再单纯依据瞬时数值，而是面向故障演化过程。
2. 字段分层采样能在保证关键感知的同时减少无效扩展字段采集。
3. 边端可靠执行链路被正式纳入算法，而非作为独立附属模块。
4. 支持异构设备统一采样与统一展示。
5. 支持实时采集和可复现实验双模式。
6. 支持从边端到后端再到前端的完整闭环。

## 十二、适用场景

本系统可用于以下场景：

1. 异构算力服务器运行状态监测。
2. 边端智能监测代理设计与实验验证。
3. GPU/NPU 热压力与故障演化分析。
4. 自适应采样算法研究与对照实验。
5. 论文、设计说明书、答辩材料和软著材料撰写。

## 十三、结论

本系统以“故障演化”为核心问题定义，以“三类控制量 + 相位驱动调度 + 字段分层采样 + 边端可靠执行链路”为关键设计主线，形成了一套适用于异构算力设备监测场景的自适应变频采样系统。该系统不仅具备算法上的自适应能力，也具备工程上的可运行性、可恢复性和可验证性，能够较好支撑后续论文、项目汇报和进一步系统扩展。
