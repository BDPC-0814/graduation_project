# 第一章 绪论

## 1.1 项目背景

随着人工智能训练、推理服务和异构算力调度场景的持续发展，单机或边端节点上同时部署 CPU、GPU、NPU 等不同类型算力设备已经成为较常见的工程形态，边缘计算相关研究也指出，靠近数据源进行处理有助于降低响应时延与带宽压力<sup>[1]</sup>。与传统仅监测 CPU 负载的系统相比，异构算力设备在监测对象、采集接口、指标结构和状态演化方式上都更复杂。一方面，CPU、GPU、NPU 的利用率、温度、功耗、显存或片上存储占用、总线吞吐等指标存在明显差异；另一方面，这些设备的状态变化并不总是线性、平滑的，很多异常或故障征兆往往表现为某些关键指标在短时间内突升、漂移、限频、重试或采集失败。如果仍然采用固定频率、全字段、全设备同步采样的方式，很容易在平稳阶段产生大量低价值样本，又在异常演化阶段因为采样不够密集而错过关键窗口。

从工程实现角度看，采样问题不仅体现在采样频率的选择上，还体现在数据缓存、异常重试、网络传输和后端落库等全过程的组织上。边端监测系统真正落地后，还必须同时面对内存缓冲积压、写盘时延、网络波动、远端接口失败、批量重试、异步回灌、数据库入库以及前端展示等一整条链路的问题。如果只设计一个理论上的风险分数，却忽略边端缓存与上传机制，系统在实际运行中仍然可能出现数据丢失、延迟升高或链路阻塞。因此，一个面向实际监测场景的系统应建立采集、调度、缓存、传输、入库、展示和评估组成的完整闭环。

基于上述背景，本项目围绕面向故障演化的异构算力设备多维风险自适应变频采样系统展开设计与实现。项目的核心思路是在保证关键状态能够被及时感知的前提下，将快线字段与慢线字段分层处理，再结合设备状态演化紧迫度、字段刷新优先级和边端执行压力三类控制量，动态决定采样相位、字段策略、传输策略与下一轮采样间隔。已有自适应采样、边缘监测和异常检测研究表明，采样频率可随信号变化、能耗约束或在线监测状态动态调整，从而减少无效采样并保留关键变化过程<sup>[2-15]</sup>。与传统固定频率方案相比，这种思路更贴近真实监测场景，也体现了将采样策略研究与系统工程实现相结合的特点。

本项目同时考虑了两类使用场景。第一类是真实设备实时采集，即直接对当前主机上的 CPU、GPU 以及边端主板上的 NPU 进行采样；第二类是可复现实验回放，即由标准回放轨迹驱动系统运行，在同一输入条件下分别执行固定频率模式和故障演化模式，并输出统一的对照报告。这种双模式设计使系统既能用于在线运行监测，也能用于离线对照分析，为策略验证和后续优化提供统一条件。

## 1.2 项目现状与意义

结合系统实现、前后端页面、实验产物和运行日志可以看出，本项目已经形成一个能够连续运行的异构算力数据采集系统原型。系统在采集侧完成了 CPU、GPU、NPU 与回放数据的统一接入，其中 NPU 侧已在亿晟科技 YS-EC588 工业级安卓/鸿蒙兼容主板上完成实机采集链路验证；在调度侧实现了面向故障演化过程的自适应变频采样；在边端侧实现了异步编排、环形缓冲、SQLite WAL 持久化和批量上传；在中心侧完成了指标、事件与告警数据的接收、存储和查询；在展示侧形成了监控仪表盘、系统控制台和告警中心等页面；在实验侧建立了回放对照、指标评估和结构化报告输出链路。由此可见，系统已经覆盖采集、调度、传输、存储、告警、可视化和实验评估等主要环节，具备较完整的数据闭环。

上述实现使本项目同时具有较明确的工程价值和研究意义。在工程应用层面，系统对异构设备指标来源不统一、采样开销与响应时效难以平衡、边端数据可靠落地和上传链路易受波动影响等问题给出了可运行的解决方案，为轻量级边端监测代理的设计提供了参考。在方法研究层面，系统围绕故障演化过程组织采样控制，将状态紧迫度、字段刷新优先级和边端执行压力纳入同一调度框架，使采样策略能够随设备状态和系统负载动态调整，体现了从固定频率轮询向场景自适应观测转变的思路。在系统验证层面，统一回放、实机采集与评估报告之间已经形成对应关系，使策略效果能够在相同输入条件下重复比较，为后续参数整定和多场景分析提供了基础。

从现阶段测试结果看，系统已经能够在统一回放和真实采集场景下体现自适应采样的实际效果。相较于固定频率方案，故障演化采样在降低低信息量重复采样、压缩数据冗余、改善长尾响应表现以及增强异常窗口局部观测能力等方面表现出一定优势，同时保持了实验结果可复核、可重复生成的特点。不同设备类型、异常模式和调度参数组合下，收益的具体表现仍会存在差异，因此围绕参数整定、事件特征匹配和多场景重复验证继续展开优化，既是系统后续完善的重要方向，也进一步说明了本项目在异构算力监测与自适应采样结合方面具有持续研究价值。

## 1.3 项目的主要内容

结合任务书中“统一模型与接口机制、自适应变频采样算法、异构算力数据采集系统开发与评估”三项主要内容，以及当前系统的实际完成情况，本项目的主要内容可概括为以下三个方面。

第一，研究异构算力设备数据采集的统一模型与接口机制，建立标准化的数据采集框架。围绕这一内容，项目首先分析了 CPU、GPU、NPU 与回放轨迹在采集来源、字段结构和状态表达上的差异，在此基础上设计了统一的数据采集接口，将设备采集过程划分为静态信息获取、快速状态采集和扩展诊断信息采集三个层次，使不同类型设备能够按照一致方式接入系统。与此同时，项目建立了统一的数据模型，对设备静态属性和动态运行状态进行规范化描述，并在动态指标中统一组织利用率、温度、功耗、内存占用、频率和异常状态等核心信息，为后续调度控制、数据存储、接口返回和前端展示提供一致的数据语义。在 NPU 侧，系统已经完成对亿晟科技 YS-EC588 工业级安卓/鸿蒙兼容主板的实机接入验证，说明统一采集框架可以从回放轨迹和传统主机设备扩展到边端嵌入式算力板。通过上述工作，项目完成了异构设备来源差异分析、统一接口接入和统一模型表达的整体设计与实现。

第二，设计基于阈值反馈与系统负载的自适应变频采样算法，实现采样频率动态调整。围绕这一内容，项目没有停留在简单的固定频率轮询上，而是结合设备状态变化和边端执行状态，设计了面向故障演化过程的调度机制。该机制一方面利用设备利用率、温度、功耗、限频标记和异常状态等信息进行阈值反馈分析，构造紧迫度和字段优先级等控制量；另一方面结合待发送数据量、缓存积压程度和上传状态等信息反映系统负载与执行压力。在此基础上，系统能够在聚焦采样、恢复观测、巡航巡检和边端降级等不同工作相位之间切换，并动态调整下一轮采样间隔、字段采样策略和数据传输策略。为了将算法真正应用到采集流程中，项目还把调度机制与快线字段、慢线字段的分层采样方式结合起来，使系统在平稳阶段能够减少不必要采样，在异常阶段能够提升关键状态的观测密度。通过上述工作，项目完成了自适应变频采样算法从策略设计到流程落地的实现。

第三，开发异构算力数据采集系统，并评估采集效率、数据冗余率与实时性指标。围绕这一内容，项目完成了从边端采样、中心接收处理到前端展示控制的系统开发。边端侧实现了采样结果的内存缓冲、持久化发送队列、异步上传和失败重试机制，用于保证采样链路在网络波动或服务暂时不可用时仍能保持基本可靠性；中心端实现了数据接收、状态存储、历史查询、事件记录和控制管理等功能；前端实现了监控仪表盘和图形化控制台，用于展示实时状态、趋势变化、事件信息和实验结果。为了完成系统评估，项目还建立了回放轨迹生成、固定频率与自适应采样对照运行以及统一指标评估流程，能够对采样点数量、数据冗余率、平均采样间隔、延迟分布、慢线激活率、缓冲上传占比和资源开销等指标进行统计分析，并输出结构化结果和图形化报告。通过上述工作，项目不仅完成了系统开发，也完成了与之配套的实验验证与指标评估。

综合来看，本项目围绕任务书提出的三项主要内容，已经完成了统一采集框架设计、自适应变频采样算法实现以及系统开发与评估验证，形成了一个具有实际运行能力和实验复现能力的系统原型。

### 2.1.1 异构设备监测与统一建模相关研究

随着边缘计算和异构算力部署的发展，设备监测对象已经从单一 CPU 扩展到 GPU、NPU 以及多种专用加速器，监测系统需要处理的数据来源、字段结构和刷新节奏也随之更加复杂<sup>[1]</sup>。在这一方向上，已有研究和工程实践普遍采用两类思路。

第一类思路是面向单类设备构建专用监测链路。这类方法通常能够充分利用设备厂商提供的驱动接口、管理命令和统计库，具有字段完备、采样精度较高和设备特性表达充分等优点。例如，GPU 监测场景中常结合厂商提供的管理接口或驱动统计能力获取利用率、功耗、显存、频率和限频状态等信息<sup>[31]</sup>。这类方法可以视为设备侧观测能力较强的实现路径，但其局限也较明显，即不同设备之间的字段命名、返回结构和调用方式差异较大，难以直接形成统一的调度、存储和展示链路。

第二类思路是面向多源数据建立统一数据表达模型。这类方法强调以通用指标语义作为中间层，将设备标识、利用率、温度、功耗、频率、错误状态和时间戳等字段进行规范化组织，再为不同设备保留必要的扩展字段。该思路的优势在于便于后续模块共享统一语义，适合构建前后端闭环系统；不足在于若抽象层设计不当，可能造成特定设备特征表达不充分。对于本课题而言，异构监测任务首先属于统一接入与统一建模问题，因此建立标准化的数据接口和统一字段模型是系统设计的前提。

从研究现状看，现有工作在单类设备高精度观测方面已经较成熟，但面向 CPU、GPU、NPU 和回放数据统一接入、统一调度和统一评估的一体化轻量级方案仍相对较少。这也是本课题在系统设计上强调统一采集接口和统一指标模型的重要原因。

### 2.1.2 自适应采样方法相关研究

自适应采样研究的核心问题是，在保证关键状态可观测的前提下，降低无效采样和系统开销。现有研究大致可以分为以下几类。

第一类是基于阈值反馈的自适应采样方法。这类方法通常根据状态量是否越过阈值、变化率是否增大或误差是否扩大来调整采样周期，具有实现简单、实时性较好和解释性较强的特点<sup>[2-4]</sup>。其优点是易于部署到资源受限环境中，缺点是阈值敏感性较强，若场景变化明显，容易出现误触发或漏触发。

第二类是面向能耗与成本权衡的自适应采样方法。这类研究通常把采样精度、通信开销和设备能耗共同纳入优化目标，根据系统资源状态或观测价值调整采样策略<sup>[5][7][15]</sup>。这类方法在无线传感器网络、物联网和周期感知场景中应用较多，能够较好地降低冗余采样，但多数研究更强调节能或通信成本，而较少直接面向异构算力设备异常演化过程中的状态感知需求。

第三类是面向异常检测或故障诊断的自适应采样方法。这类方法关注在异常发生前后提升观测密度，以提高故障识别、异常检测或状态估计效果<sup>[10-14]</sup>。与单纯节能型方法相比，它们更接近本课题的应用背景，因为其目标不是单纯降低采样次数，而是在关键时间窗口提升样本有效性。不过，这类研究多数针对单类传感器、单一业务信号或特定工业对象展开，较少把异构设备指标采集、字段分层采样和边端执行压力反馈放在同一框架下统一处理。

对本课题而言，固定频率采样仍然是最重要的对照基线。原因在于，固定频率方式简单、稳定、可重复，是传统监测系统中最常见的方案，也能够在相同输入条件下直接衡量自适应策略相对于传统方法的收益。因此，本文后续实验采用统一回放输入下的固定频率模式作为主要对照基线，将其视为评估故障演化采样有效性的强基线；而仅依赖单阈值开关、缺少边端负载反馈和字段分层机制的简化方法，更适合作为弱基线或早期原型参考。

### 2.1.3 边端可靠执行与实验评估相关研究

在边缘计算环境中，采样系统不仅要决定何时采样，还要解决采样结果如何可靠写入、缓存、传输和恢复的问题<sup>[1]</sup>。已有相关研究与工程实践表明，当采样线程、写盘线程和上传线程并发运行时，若缺少本地缓存、失败重试和持久化机制，链路很容易因瞬时网络抖动或服务短暂不可用而中断。因此，边端可靠执行问题本质上属于系统工程问题，通常需要结合内存缓冲、持久化发送队列、批量上传和指数退避重试等手段共同解决。SQLite 的 WAL 机制在这类高频写入、单机部署场景中具有较好的实用性<sup>[23]</sup>。

与可靠执行相伴随的另一个问题是实验评估。自适应采样系统的效果通常不能只用单一指标判断，而需要同时考察采样点数量、冗余率、采样间隔分布、事件响应延迟和资源开销等多维指标<sup>[3][5][7][15]</sup>。现有研究中，不少实验建立在单类传感器数据或特定场景数据集基础上，便于比较局部算法性能，但对于本课题这样同时涉及 CPU、GPU、NPU、边端传输与前后端闭环的系统而言，公开数据集与现成基准并不能直接覆盖完整任务链。因此，本课题最终采用统一回放轨迹和统一真值事件表构建可复现实验输入，并在相同输入条件下对固定频率模式和故障演化模式进行对照评估。

## 2.4 数据库软件

数据库软件是系统实现数据持久化的重要组成部分。本项目既需要保存设备最新状态、历史采样记录、事件信息和告警信息，又需要在边端暂存待上传数据，因此数据库不仅承担后端存储任务，还承担边端可靠缓存任务。结合系统规模和部署方式，项目最终采用 SQLite 作为主要数据库软件。

### 2.4.1 SQLite 数据库

SQLite 是一种轻量级嵌入式数据库，具有部署简单、依赖少、使用方便和可移植性强等特点<sup>[22]</sup>。与需要独立数据库服务器的关系型数据库相比，SQLite 以单文件形式保存数据，适合单机运行或轻量级系统原型开发。

在本项目中，SQLite 主要用于两个方面。第一，用于中心端数据持久化，保存设备状态、历史指标、事件记录、告警信息和规则信息；第二，用于边端待发送数据的本地暂存，以保证在网络暂时不可用时仍能保留采样结果。采用 SQLite 可以在不增加复杂部署成本的前提下完成系统所需的基础数据管理功能。

### 2.4.2 SQLite 的 WAL 机制

WAL 即预写式日志机制，是 SQLite 提供的一种重要事务日志模式。与传统日志模式相比，WAL 模式在读写并发、崩溃恢复和写入连续性方面具有较好表现，适合需要频繁写入的系统场景<sup>[23]</sup>。

本项目在后端数据库和边端本地缓存中都使用了 WAL 机制。一方面，后端数据库需要持续接收采样记录和事件数据；另一方面，边端本地缓存需要在采样过程中不断写入待上传记录。采用 WAL 机制能够提高系统在持续采样条件下的数据写入稳定性，并增强异常中断后的恢复能力。

## 3.1 总体需求分析

需求分析是系统开发的重要环节，也是系统设计与功能实现的基础。结合本项目的建设目标，系统需求主要包括功能需求和非功能需求两个方面。其中，功能需求主要围绕设备接入、状态采集、调度控制、数据接收、前端展示和实验评估展开；非功能需求主要围绕实时性、可靠性、可扩展性、可维护性和可复现性展开。

本项目面向异构算力设备监测场景，系统建设目标是统一接入 CPU、GPU、NPU 等不同类型设备的状态数据，对设备运行状态进行连续采集，在状态平稳时控制采样开销，在状态波动或异常出现时提高采样密度，同时保证数据在采集、缓存、上传、存储和展示过程中的连续性与可靠性，并通过对照实验对采样策略效果进行评价。

结合系统的实际实现情况，总体建设需求可归纳为以下几点：

1. 系统应能够统一接入不同来源的设备数据，包括真实主机采集数据和回放轨迹数据。
2. 系统应能够根据设备状态变化动态调整采样频率和采样内容，提高关键阶段的观测能力。
3. 系统应能够在边端环境下完成数据缓冲、持久化保存和失败重试，保证采样链路稳定运行。
4. 系统应能够在中心端完成采样结果接收、历史数据存储、事件记录和状态查询。
5. 系统应能够通过可视化界面展示设备状态、趋势变化、事件信息和实验结果。
6. 系统应能够在统一输入条件下完成固定频率与故障演化采样的对照评估，并输出结构化报告。

## 3.2 系统流程分析

在系统开发过程中，需要先对系统的主要工作流程进行分析。通过对系统运行过程的梳理，可以更清楚地了解数据在各模块之间的传递关系和处理过程。结合当前实现，系统的主要流程可以概括为设备状态获取、边端采样、调度判定、本地缓冲与上传、后端接收存储、前端展示和实验评估七个阶段。

1. 设备状态获取。实时采集模式下，系统从本机 CPU、GPU 以及边端主板 NPU 获取运行状态；回放模式下，系统从标准化轨迹文件中读取状态数据。
2. 边端采样。系统首先采集利用率、温度、功耗等快线字段，再根据需要补充频率、吞吐和错误统计等慢线字段。
3. 调度判定。系统依据设备状态变化、字段刷新需求和边端运行压力，判定当前采样阶段，并给出下一轮采样间隔和采样策略。
4. 本地缓冲与上传。采样结果先进入边端缓冲区，再写入本地持久化队列，随后由上传模块发送到中心端；若上传失败，则进入重试处理。
5. 后端接收存储。中心端接收采样结果和事件信息，并写入数据库，同时维护设备最新状态和历史记录。
6. 前端展示。前端页面通过接口获取设备状态、趋势曲线、事件信息和实验结果，并进行图形化展示。
7. 实验评估。系统在统一输入条件下运行固定频率与故障演化采样两种模式，对结果进行统计分析并输出报告。

通过上述流程可以看出，系统中的数据处理是连续进行的，各阶段之间关系紧密，前一阶段的输出直接影响后一阶段的处理结果。系统流程图如图3-2所示。

## 3.4 系统功能需求分析

系统功能需求是在总体需求和角色用例分析基础上提出的，是后续系统设计和实现的重要依据。结合当前系统实际建设内容，可以将系统功能需求归纳为设备接入与指标采集、统一字段建模、故障演化调度、边端可靠执行、后端接收与查询、前端监控展示、图形化实验控制和实验评估报告输出等几个方面。

### 3.4.1 设备接入与指标采集需求

系统应能够支持 CPU、GPU、NPU 与 Replay 四类数据来源，并通过统一接口完成状态采集。对于 CPU，应能采集利用率、频率、线程数、上下文切换率、I/O 利用率等指标；对于 GPU，应尽量采集利用率、温度、功耗、显存占用、PCIe 吞吐、时钟频率、限频原因和 ECC 信息；对于 NPU，应支持具备调试连接、设备管理命令或系统节点访问条件的目标环境，尽可能采集利用率、温度、频率、运行状态和可获得的扩展诊断字段；对于 Replay，应能从轨迹文件中按时间推进状态并完成数值插值。

### 3.4.2 统一字段建模需求

系统应避免不同设备输出格式完全不一致的情况，而是使用统一模型承载采集结果。统一模型至少需要覆盖设备标识、利用率、温度、功耗、内存占用、频率、错误状态、采样时间戳和采样间隔等通用字段，同时允许 CPU、GPU、NPU 保留各自特有字段，以便后端查询和前端展示可以采用一致方式处理。

### 3.4.3 故障演化调度需求

系统应能够依据设备状态变化调整采样行为，而不是长期使用固定间隔。调度结果不仅应输出下一个采样间隔，还应输出当前采样相位、字段采样策略和传输策略。系统还应支持快线字段与慢线字段的分层采样机制，使平稳阶段以轻量采样为主，异常阶段再补充诊断字段。

### 3.4.4 边端可靠执行需求

系统应在边端环境下支持数据缓冲、落盘和失败重试，避免网络故障导致采样主循环阻塞或数据直接丢失。为满足该需求，系统至少需要具备内存缓冲、持久化 outbox、批量上传、重试退避和死信处理等能力。

### 3.4.5 后端接收与查询需求

系统应提供统一的数据接收接口，能够接收边端批量上传的指标和事件，并将其写入数据库。系统还应提供设备列表、实时指标、历史曲线、对比曲线、日志、事件和实验评估等查询接口，以支撑前端页面正常显示。

### 3.4.6 前端监控展示需求

系统应提供可视化页面，用于展示设备总体状态、实时趋势、活动日志和实验结果。界面不要求达到企业平台级复杂度，但应满足基本的可读性、模块划分清晰性和状态刷新能力。

### 3.4.7 图形化实验控制需求

系统应提供脚本或页面来统一启动实时采集、回放轨迹生成和回放对照实验，避免操作者每次都手工输入长命令。对于当前项目而言，这一需求已经落实为 PowerShell 启动脚本与前端图形化控制台两种入口。

### 3.4.8 实验评估与报告输出需求

系统应能在统一输入条件下比较固定频率采样与故障演化采样，并输出结构化评价结果。评价维度至少应包括采样点数量、冗余率、平均采样间隔、延迟分布、慢线激活率、缓冲上传占比以及资源开销等指标。

## 3.5 非功能需求分析

### 3.5.1 实时性需求

系统需要具备基本实时性。所谓实时性，在本项目中并不要求硬实时或毫秒级严格截止，而是要求系统能够按设定周期稳定采样、按较短轮询周期刷新前端数据，并在异常状态出现时支持更密集的观测。当前实现中，仪表盘不同模块采用 3 秒到 15 秒不等的轮询频率，控制台状态采用 2.5 秒轮询，后端接收链路支持边端批量回灌，基本满足当前系统的实时展示需求。

### 3.5.2 可靠性需求

系统必须具备基本的链路可靠性。由于采样端与后端之间通过 HTTP 接口交互，网络波动、接口暂时不可达和采样期间程序中断等问题都可能出现。因此，系统必须通过本地缓冲与 SQLite WAL 持久化机制保证数据不会因瞬时故障而完全丢失，并通过失败重试与死信状态区分不同故障等级。

### 3.5.3 可扩展性需求

系统应具备扩展新设备、新字段和新策略的能力。当前项目中，设备采集部分采用统一适配器抽象机制，前后端数据结构通过统一模型组织，后端数据库字段也预留了较丰富的扩展列，这些都使系统具备继续接入更多类型设备和更复杂评价指标的可能性。

### 3.5.4 可维护性需求

系统代码应具备明确的模块边界，便于定位问题与后续修改。从仓库结构上看，当前项目已经将设备适配、调度算法、运行时、后端、前端和实验脚本分开组织；从脚本层看，也提供了统一启动与统一评估入口，这些都提升了可维护性。

### 3.5.5 可复现性需求

对于此类实验型监测系统而言，可复现实验链路十分重要。因此，系统必须具备标准回放轨迹、统一 ground-truth 事件表、固定与演化两种模式在同一输入上运行以及结果生成 JSON 与 Markdown 报告的能力。当前项目已经具备这一链路。

## 3.6 数据分析

系统中的数据对象可以分为五类。第一类是设备最新状态数据，对应设备当前是否在线、最新利用率、温度、功耗、采样间隔、演化分数和采样相位等信息，主要用于前端总览。第二类是历史指标数据，对应每次采样写入的明细记录，是系统最核心的数据主体。第三类是事件数据，对应采集异常、告警打开、告警恢复、告警确认、告警静默等事件。第四类是告警与规则数据，用于描述阈值规则及其当前触发状态。第五类是实验报告数据，用于总结 fixed 与 evolution 两种模式的对照结果。

从数据流角度看，设备适配器首先产生原始动态指标，单设备采样器在其上补充调度结果和边端状态，边端代理再将这些结构化记录写入 outbox 并上传，后端接收后分别写入指标表和事件表，前端通过概览接口、历史接口和实验接口拉取对应数据。从这一过程可以看出，数据需要经过采集、调度、封装、传输、入库和展示等多个处理阶段，并在各阶段不断补充上下文语义。

结合系统的数据范围，本章数据分析重点关注监控与实验数据对象，主要包括设备状态、采样指标、调度结果、事件记录、告警对象和评估结果等内容。

# 第四章 系统概要设计

本章在第三章需求分析的基础上，对系统的总体组织方式进行概要设计说明。内容包括总体设计原则、总体架构、功能模块、数据库对象、接口划分以及软硬件环境等方面，目的是明确各组成部分的职责边界、数据流向与部署关系，为下一章详细设计奠定结构基础。

## 4.1 系统总体设计原则

在完成需求分析之后，系统总体设计需要围绕异构设备监测、故障演化采样和边端可靠执行三个重点展开。根据系统实现情况，概要设计遵循以下原则。

第一，统一抽象优先原则。CPU、GPU、NPU 以及回放轨迹在原始数据格式、采样方式和字段完备度上都不相同，如果直接在后端和前端处理异构原始格式，系统复杂度会迅速上升。因此设计上首先通过统一指标模型对利用率、温度、功耗、频率、内存、异常状态等信息进行标准化表达，使调度器、边端代理、后端存储和前端展示都围绕同一套字段语义工作。

第二，调度与采集解耦原则。设备接入部分负责获取设备状态并完成统一字段整理，采样调度部分负责决定采样相位、字段策略和时间间隔。这样的划分使设备适配逻辑与策略逻辑相互独立，便于后续调整算法而不影响底层采集实现。

第三，边端可靠优先原则。采样链路需要兼顾连续观测和稳定传输，因此系统在边端设置了环形缓冲、SQLite WAL 持久化发送队列、批量上传与失败重试机制，保证采样主循环不会因网络抖动或中心服务短时不可用而中断<sup>[23]</sup>。

第四，实验可复现原则。为了保证实验结果能够被重复验证，系统专门设计了回放轨迹生成、固定频率对照、演化模式对照、统一评估脚本和结构化报告输出链路，从而避免结论仅依赖一次性运行截图。

第五，前后端闭环原则。系统由边端采样、中心服务和浏览器界面共同构成。后端既承担数据接收与存储，也承担概览、历史、事件、实验和控制能力的统一输出；前端承担状态展示、任务触发和结果查看等职责，从而形成完整闭环。

第六，实事求是原则。系统概要设计以实际运行结构为依据，模块划分、接口组织和数据库对象均围绕真实存在的功能展开，确保论文表述与系统实现一致。

## 4.2 系统总体架构设计

### 4.2.1 网络架构设计

从网络拓扑角度看，系统可以划分为边端采样侧、中心服务侧和浏览器访问侧三部分。边端采样侧负责直接接触设备或回放轨迹，中心服务侧负责统一接收与持久化，浏览器访问侧负责可视化监控和实验控制。联调阶段三部分可以部署在同一台主机上，也可以按照边端与中心端分离的方式部署。无论采用哪种部署方式，这三部分的职责边界保持一致。

边端采样侧内部可进一步划分为设备接入层、采样调度层和可靠上传层。设备接入层通过操作系统资源库、硬件管理命令或回放文件获取原始状态；采样调度层根据设备状态、变化趋势和执行压力生成采样决策；可靠上传层负责把结构化记录缓冲、持久化并上传到中心接收接口。中心服务侧由应用接口层、数据处理层、SQLite 持久化层和控制服务组成。浏览器访问侧通过轮询方式获取概览、历史、事件和实验结果。

当前实现采用 HTTP 作为边端与中心之间的统一通信协议。其优点在于实现简单、可调试性强、适配本课题规模；缺点是缺少天然的消息队列削峰能力。为弥补这一点，系统在边端增加了本地发送队列机制，等价于在应用层补充了一层轻量消息缓冲。对于当前单机或小规模部署场景，这种网络结构在复杂度和可用性之间取得了较好平衡<sup>[19]</sup>。

### 4.2.2 系统架构设计

从软件结构角度，系统整体采用采样执行层、服务支撑层和展示控制层三层架构。

第一层为采样执行层，负责设备接入、统一建模、采样调度、边端缓冲、持久化发送和上传控制，是系统运行链路的起点。

第二层为服务支撑层，负责 HTTP 服务、数据接收、记录写入、规则评估、查询聚合和实验任务编排，是前后端闭环的核心枢纽。

第三层为展示控制层，负责页面组织、图表展示、状态轮询和任务交互，把后端数据转换为面向观察者和操作者的界面结果。

按照运行顺序，系统主要经过以下链路：设备状态产生后进入适配器；适配器输出统一指标对象后进入单设备采样器；采样器结合调度器决定字段策略和采样间隔；边端代理将结果写入环形缓冲并刷入本地发送队列；上传线程批量压缩并发送到后端；后端入库后生成概览、历史、日志、事件与实验查询结果；前端轮询并绘制统计卡片、曲线图、任务进度和实验结果。

系统研发过程中曾形成过多种调度原型。论文中的总体架构以最终形成闭环运行的主链路为准，即以统一设备接入、故障演化调度、边端可靠执行、中心数据服务和前端监控控制组成的整体结构为主。

### 4.2.3 故障演化采样控制模型

为了说明系统为何采用当前架构，本节对故障演化采样控制模型进行归纳。系统先计算紧迫度、字段优先级和执行压力三个控制量，再综合得到控制分数，最后映射为采样相位、字段策略和采样间隔。

为了统一不同量纲的指标，系统先定义一个分段归一化函数：

```text
公式4-1 分段归一化函数
           0,                    x <= l
S(x;l,u) = (x - l) / (u - l),   l < x < u
           1,                    x >= u
```

其中，`x` 表示待评估指标值，`l` 表示该指标进入关注区间的下界，`u` 表示该指标达到饱和关注程度的上界。`S(x;l,u)` 的取值范围为 `[0,1]`，其作用是把利用率、温度、功耗、漂移量等不同量纲的值投射到统一尺度上。

在此基础上，调度器计算设备自身的紧迫度 `U`。依据系统实现，紧迫度可整理为：

```text
公式4-2 紧迫度计算式
U = clamp(
      16·S(u;28,88)
    + 16·S(max(u-u_b,0);5,20)
    + 20·S(Δu;6,22)
    + 12·S(T;55,T_lim)
    + 6·S(max(T-T_b,0);1,8)
    + 6·S(M;55,95)
    + C_P
    + 18·β_th
    + 24·β_err
    )
```

其中，`u` 表示当前利用率百分比，`u_b` 表示利用率基线，`Δu` 表示相邻两次采样的利用率变化幅度，`T` 表示芯片温度，`T_b` 表示温度基线，`T_lim` 表示热设计限制温度，系统默认取 `85℃`，`M` 表示显存或内存利用率百分比；`β_th` 为限频标记，当存在限频状态时取 1，否则取 0；`β_err` 为异常标记，当状态异常、存在错误描述或存在错误码时取 1，否则取 0。`clamp` 函数用于把结果限制在 `[0,100]` 区间内。式中的功耗项 `C_P` 分两种情况处理：当设备提供功耗上限时，采用功耗占上限比例进行归一化；否则使用功耗绝对值区间进行近似映射。需要说明的是，式4-2给出的数值是当前系统的通用默认配置；在 Windows 实时联调中，为避免 Intel 核显在中低负载下过早进入恢复观测，工程实现又为集成 GPU 分支单独抬高了利用率、漂移和跳变项的触发阈值，使其更符合低功耗图形设备的运行特征。

字段优先级 `F` 反映当前轮次是否需要补采慢线诊断字段。根据当前代码实现，可整理为：

```text
公式4-3 字段优先级计算式
F = clamp(
      10·S(k;0,N_s+2)
    + 24·S(max(Δu,2ΔT,ΔP/4);2,16)
    + 18·S(max(u-u_b,0);1,14)
    + 10·S(max(T-T_b,0);0.5,6)
    + 8·S(max(P-P_b,0);2,30)
    + 16·β_f
    )
```

其中，`k` 表示距离上一次慢线采样已经过去的快线轮次数，`N_s` 表示慢线刷新阈值周期数，当前实现默认值为 6；`ΔT` 为相邻两次温度变化量，`ΔP` 为相邻两次功耗变化量，`P` 为当前功耗，`P_b` 为功耗基线；`β_f` 为字段补采触发标记，当出现限频或异常状态时取 1，否则取 0。`N_s` 取 6 的依据是希望慢线字段在平稳阶段保持比快线更低的刷新频率，但又不至于长时间失去诊断参考。若按当前常见 `1s~6s` 的采样节奏估算，慢线在低风险场景下通常可控制在数秒到数十秒尺度内完成一次刷新，既能压低重字段采集成本，又能避免慢线信息长期陈旧。与早期版本相比，当前实现显著降低了慢线陈旧度在字段优先级中的权重，以避免系统仅因慢线长期未刷新，就在低风险阶段过度缩短采样间隔。该式表明系统除在异常明显时补采慢线字段外，也会在慢线长期未刷新或波动逐渐增强时安排分层刷新。

边端执行压力 `E` 用于描述本地缓冲与上传链路对采样系统本身的反作用。其计算方式如下：

```text
公式4-4 执行压力计算式
E = clamp(
      28·S(n_p;40,300)
    + 35·S(n_d;0,10)
    + 25·r_b
    + 10·β_o
    )
```

其中，`n_p` 表示本地发送队列中的待发送记录数，`n_d` 表示死信记录数，`r_b` 表示环形缓冲区积压比例，即 `ring_backlog / ring_capacity`，`β_o` 表示上传离线惩罚项，当上传器未激活且本地仍存在待发送或缓冲积压时取 1，否则取 0。与前期更敏感的配置相比，当前实现把待发送记录的显著影响区间后移到 `40~300`，目的是避免系统因少量历史积压就长期误判为高压力状态。该区间并非任意给定，而是依据日常空闲、短时抖动和持续阻塞三类运行样本联调得到：当待发送记录少于 40 条时，多数属于上传线程可快速消化的瞬时波动；当待发送记录持续接近或超过数百条时，才说明上传速率已经明显落后于采样写入速率。因此，把敏感区间设置在 `40~300` 有助于减弱轻微堆积带来的误触发，同时保留对持续拥塞状态的放大能力。该式体现出系统既观察设备本身，也观察观测链路的运行压力。

最终控制分数 `C` 由三个控制量共同决定：

```text
公式4-5 控制分数计算式
C = clamp(0.52·U + 0.36·F - 0.30·E)
```

式中 `0.52`、`0.36` 和 `0.30` 为当前实现采用的经验权重。这组权重来源于回放对照实验与在线联调的折中结果：若紧迫度权重过低，系统在异常前沿阶段不易及时收紧间隔；若字段优先级权重过高，系统容易因慢线长期未刷新而频繁补采；若执行压力抑制项过弱，则缓冲积压和待发送增长时仍可能维持激进采样。当前取值使紧迫度成为主导项，字段优先级作为辅助放大项，执行压力作为制动项参与决策，能够较好兼顾异常响应、补采价值与链路稳定性。

其中，`U` 为紧迫度，`F` 为字段优先级，`E` 为执行压力。该式体现出系统在异常明显时优先保证观测能力，在边端压力升高时适当抑制采样强度。

控制分数计算完成后，调度器进一步判定系统处于聚焦采样、恢复观测、巡航巡检或边端降级四种相位之一，并生成字段策略和传输策略。其中，聚焦采样对应最小间隔快速采样，恢复观测强调短周期连续观察，巡航巡检强调轻量化快线与周期性慢线刷新，边端降级则在执行压力过大时优先保证链路存活。当前版本还对传输策略做了保守性修正：系统仅在缓冲积压达到一定规模，或者缓冲非空且待发送记录数超过阈值时，才进入缓冲上传状态。

## 4.3 系统功能模块概要设计

### 4.3.1 设备接入与统一建模模块

该模块负责从真实设备或回放文件中提取原始运行状态，并映射为统一动态指标对象。对于 CPU 侧，主要采集利用率、频率、线程数、上下文切换和 I/O 等系统层指标；对于 GPU 侧，重点采集利用率、温度、功耗、显存、频率、总线吞吐和限频状态；对于 NPU 侧，系统通过设备管理命令、调试连接和板端系统节点等方式获取可用指标，并已在亿晟科技 YS-EC588 工业级安卓/鸿蒙兼容主板上完成采集链路验证；对于回放数据，则按照时间轴推进读取轨迹记录。

从概要设计角度看，该模块的关键任务是保证不同来源的数据都能以统一格式进入后续链路，因此它主要负责数据可得性和基本字段整理，不直接承担策略判断。

### 4.3.2 故障演化调度模块

该模块由故障演化调度单元和单设备采样单元共同构成。前者负责控制量计算与策略生成，后者负责把策略落实到一次具体采样中，包括是否只采快线字段、是否补采慢线字段、下一次采样间隔以及采样结果结构化封装。

概要设计上，该模块实现了采样时间控制和字段层级控制两条主线。相比传统定时轮询方式，它能在状态平稳时减少无效采样，在波动增强时收紧间隔并补采更多诊断字段，是整个系统最具研究意义的功能模块。

### 4.3.3 边端可靠执行模块

该模块由内存缓冲、持久化发送队列、批量上传单元和边端运行代理组成。内存缓冲负责线程安全的短时削峰，持久化发送队列负责保存未发送记录，批量上传单元负责网络发送，边端运行代理则把采样线程、写盘线程和上传线程组织在一起。

该模块在概要设计中的定位是观测链路稳定器。其作用是保证后端短时不可用或网络延迟升高时，边端采样仍可持续运行，前端数据展示与实验结果也能保持完整。

### 4.3.4 后端数据服务模块

该模块由 FastAPI 接口层、数据库服务层和数据聚合层组成。接口层负责暴露统一 API，数据库服务层负责 SQLite 表结构维护、记录写入和查询封装，数据聚合层负责概览汇总、历史查询、对比查询、事件筛选、实验报告读取以及告警规则处理。

后端采用轻量化组织方式，由应用服务直接管理 SQLite 数据库和实验产物目录。对于系统当前规模，这种设计既降低了部署难度，也保证了逻辑链路完整。

### 4.3.5 前端监控与控制模块

该模块由 React 页面、图表组件、轮询钩子和 API 调用封装组成，主要包含两个一级视图：仪表盘页面和控制台页面。仪表盘页面负责设备状态总览、趋势分析、事件日志和实验评估展示；控制台页面负责轨迹生成、实时采集、回放对照、任务跟踪和产物查看。

前端页面结构围绕监测观察和实验控制两类任务展开，一级视图设置为仪表盘页面和控制台页面，功能组织强调状态总览、趋势分析、事件查看、任务触发和结果回看。

## 4.4 数据库概要设计

### 4.4.1 概念数据模型设计

结合系统实现，系统核心数据对象包括设备、指标、事件、告警、告警规则和边端发送队列六类。其中设备对象用于保存每个设备的最近状态快照；指标对象用于记录每一次采样的历史明细；事件对象用于记录异常、告警开闭和系统行为；告警对象用于记录规则触发后的生命周期状态；告警规则对象用于定义阈值条件；发送队列对象位于边端 SQLite 中，用于保存待上传记录。

从概念层看，设备与指标之间是一对多关系，一台设备会产生多条历史指标；设备与事件之间也是一对多关系；设备与告警之间同样是一对多关系；告警规则与告警之间是一对多关系，一个规则可在不同设备或不同时刻触发多个告警实例。与此同时，发送队列不直接作为中心数据库实体参与业务查询，它属于边端可靠传输链路的数据缓冲实体。

### 4.4.2 E-R 图设计

若以 E-R 模型表达，可以将设备视为中心监测实体，指标、事件和告警分别作为其历史观测、行为记录和异常状态扩展实体；告警规则作为规则实体与告警建立关联；发送队列记录则作为边端独立实体存在，不与中心数据库建立强外键关系。之所以不对发送队列设置跨库外键，是因为它位于边端本地数据库中，服务于离线重试，不属于中心端的一致性约束范围。

## 4.5 系统接口概要设计

### 4.5.1 外部接口设计

系统外部接口主要包括三类。第一类是设备采集接口，即对操作系统资源库、GPU 管理命令、NPU 管理命令以及回放轨迹文件的访问。第二类是中心服务 HTTP 接口，包括数据接收接口、设备查询接口、指标查询接口、事件查询接口、概览接口、实验评估接口和控制接口。第三类是文件产物接口，即系统通过本地文件系统读写实验轨迹、事件文件、结构化报告和图像结果。

概要设计中，外部接口强调统一、轻量和可替换。比如设备采集层允许不同适配器对接不同命令行工具，但对上层暴露统一指标模型；前端不直接读取数据库，而只通过 HTTP API 获取结果；实验报告不直接嵌入数据库，而以文件形式输出并由后端统一读取。

### 4.5.2 内部接口设计

系统内部接口主要分布在四个方向。其一是设备接入单元与采样单元之间的接口，核心是获取快线字段和按需补采慢线字段；其二是采样单元与调度单元之间的接口，核心是输入当前指标与运行时反馈，输出采样决策；其三是边端代理与发送队列、上传单元之间的接口，核心是记录入队、批量持久化、到期取出、上传成功确认和失败重试；其四是后端接口层与数据服务层之间的接口，核心是按视图组织查询结果而不暴露底层 SQL 细节。

## 5.1 系统流程设计

### 5.1.1 实时采集流程设计

实时采集流程是本系统最基础、最常运行的一条主链路，其执行步骤可以概括为设备发现与适配、单设备采样、调度决策、记录结构化、本地缓冲、中心入库和前端展示。

系统启动后，控制服务或实验脚本根据参数选择相应设备类型，并为每个设备实例化一个采样单元。边端代理负责管理多个采样单元的并发调度以及写盘、上传等后台线程。

在每一轮采样中，采样单元首先获取快线指标，包括利用率、温度、功耗、内存占用、错误码和状态标记等优先级较高、获取成本较低的内容。如果当前模式为固定频率，则系统按照固定轮次决定是否补采慢线字段；如果当前模式为故障演化采样，则采样单元把快线结果和运行时反馈一并送入调度单元，由后者输出采样相位、字段策略、传输策略和下一次采样间隔。

当调度单元判定需要补采慢线字段时，设备接入层会额外采集频率上限、总线吞吐、错误计数、线程数、上下文切换率和 I/O 利用率等字段，并与快线结果合并成一次完整采样记录；若不需要补采，则系统复用上一次慢线字段快照，只更新当前快线字段，以降低采样开销。最终生成的记录既包含设备状态，也包含采样相位、字段策略、传输策略、控制分数和下一次采样间隔等上下文信息。

随后，记录由边端代理写入环形缓冲区，后台写盘线程批量刷入本地发送队列；上传线程再根据到期条件取出待发送记录并提交给中心接收接口。后端收到记录后，按照指标记录和事件记录两类分别入库，并同步更新设备最新快照。前端仪表盘通过轮询接口拉取这些结果，形成实时总览、趋势图和日志窗口。

### 5.1.2 回放对照实验流程设计

为了完成统一评估与对照分析，本系统在实时采集流程之外实现了完整的回放对照实验流程。该流程通常由控制台页面或控制服务触发，执行顺序为“准备回放轨迹—运行固定频率实验—运行演化采样实验—执行统一评估—发布并展示报告”。

首先，系统根据需要生成标准化回放轨迹文件和对应事件文件。轨迹文件保存时间轴上的设备状态变化，事件文件保存统一真值事件，用于后续延迟评价。完成轨迹准备后，系统在同一份输入轨迹上先后运行固定频率模式和故障演化模式，分别得到两组指标文件、事件文件以及边端发送记录。

两轮实验完成后，系统调用统一评估程序读取两组结果，并在统一参数下计算采样点数量、冗余率、采样间隔统计、资源开销、行为特征以及基于真值事件的延迟分布，最终输出结构化报告、统计表和图像文件。控制服务再将最新结果发布到统一结果目录，供前端仪表盘的实验评估视图统一读取。

这一流程的关键价值在于保证对照公平性。固定频率模式和演化采样模式在同一份回放轨迹上分别执行，从而减少输入差异对结果的干扰。

### 5.1.4 异常与告警联动流程设计

系统中的异常联动流程包含两条路径。第一条路径是采样单元在快线采集阶段发现设备状态异常或采集失败，此时采样结果中的状态字段会被置为异常，并可能伴随错误码或错误描述；第二条路径是后端在写入指标或事件时根据规则表执行判定，生成或恢复告警。

以指标型告警为例，后端在接收每一条指标记录后，会检查默认规则，如设备不可用、故障演化高紧迫度、温度过高等。一旦某条规则满足条件，系统就在告警表中打开或更新一条告警记录，并向事件表写入告警开启类事件；当条件恢复正常且规则支持自动恢复时，再将该告警标记为已恢复，并写入告警恢复类事件。对于事件型告警，当接收到采集器不可用等特定事件时，系统也可直接基于事件来源触发告警。

这一联动流程的设计意义在于，将瞬时阈值异常转化为具有生命周期状态的告警实体，使前端能够围绕告警状态开展展示与管理，并为后续扩展确认、静默和关闭等操作提供数据基础。

### 5.2.1 设备接入与采样模块详细设计

设备接入模块的核心设计是以统一适配机制屏蔽设备差异，以采样单元组织采样行为。系统首先定义统一适配器抽象接口，然后由 CPU、GPU、NPU 与回放四类适配器分别实现。CPU 适配器关注利用率、频率、线程数、上下文切换和 I/O 等系统层指标；GPU 适配器除基础利用率外，还进一步采集功耗、显存、温度、频率、总线吞吐、限频与错误计数信息，相关指标类型与常见 GPU 管理接口提供的设备状态信息相对应<sup>[31]</sup>；NPU 适配器采用可插拔后端设计，可对接通用设备管理命令，也可通过 OpenHarmony/HDC 调试连接或 Rockchip 类 sysfs/debugfs 节点获取板端 NPU 状态；回放适配器则根据时间推进从轨迹文件中读取并插值，模拟真实设备状态演化过程。

在亿晟科技 YS-EC588 工业级安卓/鸿蒙兼容主板实验中，系统采用板端调试连接方式访问 NPU 相关内核节点，完成了静态信息读取、快线指标采集和慢线扩展字段补采。快线侧主要关注 NPU 利用率、温度和运行状态，慢线侧主要关注频率、频率上限、调速策略、限频判断和复位计数等诊断字段。采集结果进入统一动态指标模型后，与 CPU、GPU 和回放轨迹产生的数据使用相同的采样、调度、入库和展示流程处理。

在适配器之上，单设备采样器负责把一次采样行为组织为可直接使用的结构化样本。其内部状态至少包括当前模式、固定采样间隔、演化模式上下界、上一次慢线字段快照、慢线距离上次采样轮数以及运行时反馈等。每轮采样先获取快线指标；如果设备状态异常，系统直接转入高优先级观测决策；如果设备状态正常，则根据当前模式决定是否补采慢线字段。

快线字段和慢线字段的划分是本系统的重要实现细节。快线字段强调高频、轻量、每轮必采，例如利用率、温度、功耗、内存利用率、错误码和状态；慢线字段强调诊断性、补充性和较高采集成本，例如频率上限、PCIe 吞吐、ECC 累计错误、线程数、上下文切换率和 I/O 利用率等。通过这一划分，系统避免了把所有字段都按同一频率采集，从而为自适应采样创造了实现基础。

为了保证慢线字段在不采集时仍能维持结构完整性，采样器会保留上一次慢线结果作为缓存，当本轮未补采慢线时，将快线字段与缓存慢线字段合并后再输出。这样做虽然会带来少量慢线字段时效性略低的代价，但能显著降低频繁采集重字段带来的开销，符合本项目的设计目标。

### 5.2.2 故障演化调度模块详细设计

故障演化调度模块是本系统算法层的核心。其详细设计可分为四个步骤：基线更新、控制量计算、相位判定和策略输出。

第一步是基线更新。系统使用指数滑动平均维护利用率、温度和功耗基线。指数滑动平均是时间序列平滑和在线监测中常用的递推估计方法，适合在不保存完整历史序列的情况下刻画近期状态水平<sup>[32]</sup>。若记上一时刻基线为 `B(t-1)`，当前观测值为 `x(t)`，平滑系数为 `α`，则基线更新公式为：

```text
公式5-1 指数滑动平均基线更新公式

B(t) = B(t-1) + α · [x(t) - B(t-1)]
```

其中，`B(t)` 表示当前时刻基线，`B(t-1)` 表示上一时刻基线，`x(t)` 表示当前实际观测值，`α` 表示平滑系数。当前代码默认基础平滑系数为 `0.12`，当系统处于聚焦或恢复相位时，会把该系数乘以 `0.55`，以减缓异常阶段对长期基线的污染，从而降低短时噪声对长期基线的拉动。上述参数来自在线联调与回放复核的共同结果。基础平滑系数若取得过大，基线会过快追随瞬时波动，导致后续基于偏离量的判断变得不敏感；若取得过小，基线又会更新过慢，难以反映设备在较长时间尺度上的负载迁移。将基础值设置为 `0.12`，可以使基线在平稳运行时保持一定跟随能力，同时不过度贴近单次抖动。异常相位下再乘以 `0.55`，相当于把有效平滑系数降低到 `0.066`，这样可以避免异常尖峰迅速抬高长期基线，使系统在设备恢复后仍能较清楚地区分正常水平与异常残余影响。

第二步是控制量计算。调度器基于第四章给出的紧迫度、字段优先级和执行压力计算式，得到三个 `[0,100]` 范围内的控制量，再计算综合控制分数。实现中，展示层和数据库仍沿用 `evolution_score` 字段名称表示紧迫度控制量，以保持前后链路命名一致。

第三步是相位判定。当前实现中，当设备异常、紧迫度高于 58、控制分数高于 50，或者紧迫度与字段优先级同时达到较高阈值时，系统进入聚焦采样；当执行压力高于 78 且紧迫度不算过高时，系统进入边端降级；当紧迫度达到 30、字段优先级达到 40 或控制分数达到 28 时，系统进入恢复观测；其余情况下保持巡航巡检。这几组阈值是在多轮回放样本和实时采样联调中逐步收敛得到的。聚焦阈值设置在 `50~58` 附近，目的是让系统只在异常征兆已经较明确时进入最激进的高频观测，避免中低负载波动频繁触发聚焦；恢复阈值设置在 `28~40` 区间，目的是让系统在异常刚刚减弱时仍保持短时间连续观察，而不是过早回到巡航状态；执行压力阈值取 `78`，则是为了把边端降级保留给明显积压或上传受阻场景。调度器还保留了聚焦保持周期和恢复保持周期，用于避免状态在临界点附近频繁抖动。经过联调，恢复保持周期已收敛为较短的 1 轮，以减少 CPU 与低功耗 GPU 在轻微波动下被长时间滞留在恢复相位中的现象。该设置的好处是既能抑制相位震荡，又不会让系统在风险已经回落后继续维持过高采样密度。

第四步是策略输出。相位确定后，系统根据当前状态选择字段策略与传输策略，并计算下一次采样间隔。当前联调后的默认上下界为 `t_min=1.0s`、`t_max=6.0s`。这一上下界并非随意设定，而是结合回放轨迹步长、主机侧采样开销和边端上传能力折中得到：下界需要足够小，才能在异常窗口内体现局部加密观测能力；上界又不能过大，否则平稳阶段相邻观测点间距会被拉得过长，不利于感知缓慢漂移类故障。聚焦相位一般采用最小间隔和全量聚焦字段策略；恢复相位依据控制分数、字段优先级和是否触发慢线补采，主要落在 `1.5s、2.5s、3.0s、4.0s` 四个等级；巡航相位根据字段优先级与执行压力决定 `4.0s、5.5s、6.0s` 等较稀疏间隔；边端降级相位则在保证一定观测能力的前提下主动放缓频率。传输策略方面，系统优先保持直传，仅在环形缓冲积压达到较高水平，或缓冲非空且待发送记录数已明显增长时，才切换到缓冲上传。策略输出同时考虑设备状态、字段价值和链路压力。

### 5.2.3 边端可靠执行模块详细设计

边端可靠执行模块以边端代理为运行核心，由主采样线程池、写盘线程和上传线程协同工作。主采样线程池负责并发驱动多个单设备采样器，并根据每个设备的下一次到期时间进行调度；写盘线程负责从环形缓冲区中批量取出记录并刷入本地发送队列；上传线程负责从发送队列中取出到期记录并尝试发送到后端。

其中，环形缓冲区的作用是把高频采样结果先暂存到内存中，避免主采样线程直接阻塞在数据库写入或网络上传上。本地发送队列的作用则是把内存中的待发送记录进一步持久化，保证即便进程短暂中断，也不会把尚未上传的数据全部丢失。由于该发送队列使用 SQLite WAL 模式，因此能够在读写并发和崩溃恢复之间取得较好的实用平衡<sup>[23]</sup>。

上传失败时，系统不会立即丢弃记录，而是采用指数退避策略重新安排下次重试时间。若记当前时间为 `t_now`，基础重试延时为 `t_base`，最大延时为 `t_max`，当前尝试次数为 `a`，则重试时间可表示为：

```text
公式5-2 指数退避重试公式

t_retry = t_now + min[t_max, t_base · 2^(a-1)]
```

其中，`t_retry` 表示下一次允许重试的时间，`t_now` 表示当前失败发生时间，`t_base` 表示基础重试间隔，当前实现默认取 1 秒，`a` 表示当前尝试次数，`t_max` 表示最大退避上限，当前实现默认取 60 秒。当尝试次数达到上限后，记录会被标记为 `dead`，不再参与正常上传流程。基础间隔取 1 秒，是为了让偶发网络抖动或短时服务忙碌能够被快速重试消化；最大退避上限取 60 秒，是为了防止在远端持续不可用时上传线程以过高频率重复失败，进而占用边端 CPU 和 I/O 资源。这组参数的好处在于，短故障场景下恢复较快，长故障场景下又能有效抑制无效请求风暴。

为了让调度器感知边端执行压力，边端代理还会周期性统计待发送记录数、死信记录数、环形缓冲积压数量以及上传器是否可用，并将其封装为运行反馈输入调度器。这样，可靠执行模块同时承担链路保障和调度反馈两项职责。

### 5.2.4 后端数据服务模块详细设计

后端数据服务模块由入口接口、数据解析、数据库写入、规则评估和查询聚合五部分构成。以数据接收接口为例，服务收到请求后先检查内容编码，必要时进行解压，再解析 JSON 结构并提取记录数组。数组中的每个元素都包含记录类型和记录内容，后端按类型分别送入指标写入或事件写入逻辑。

在指标写入时，后端会把统一字段模型中的数值写入 `metrics` 表，同时根据 `device_id` 更新 `devices` 表中的最新设备快照。`devices` 表用于维护每台设备的当前状态视图，历史时序数据则持续保存在 `metrics` 表中，便于前端分别完成概览展示和历史曲线查询。

在事件写入时，后端将记录插入 `events` 表，并保留时间戳、设备编号、事件类型、严重等级、消息、详情与来源等字段。无论是指标还是事件，只要入库成功，系统都会继续执行相应的告警规则评估逻辑。默认规则包括设备不可用、故障演化高紧急度、温度过高以及采集器异常四类，它们分别覆盖状态异常、控制量异常、温度异常和事件异常。

在查询聚合方面，后端分别提供概览汇总、单设备历史、多设备对比、最近日志和实验报告读取等服务，从而为前端各视图提供稳定的数据来源。这样，前端所见到的每一种数据视图，都有清晰的后端聚合入口。

### 5.2.5 前端监控与控制模块详细设计

前端采用双视图单页结构，一级界面由监控仪表盘和实验控制台组成。这样的页面组织与系统使用场景一致：观察者主要停留在仪表盘，操作者主要停留在控制台。

仪表盘页面内部划分为总体概览、实时趋势、事件日志和实验评估四个功能区域。总体概览区域展示设备总数、在线数量、高风险设备数、平均采样间隔等摘要信息，并配合设备状态卡片和快照表格显示当前设备态势；实时趋势区域展示利用率、演化分数和采样间隔曲线；事件日志区域展示最近事件和最近日志；实验评估区域展示固定频率与故障演化采样的对照结果及相关曲线图。

控制台页面面向实验操作者设计，主要包含任务参数区、任务进度区、任务日志区和最近任务区。任务参数区支持回放轨迹生成、实时采集和回放对照三类操作；任务进度区显示后台任务状态、当前步骤、步骤执行结果和产出文件路径；任务日志区滚动显示控制服务汇总的脚本输出；最近任务区便于操作者回顾近期实验。页面通过周期轮询任务状态接口获取最新任务状态，因此在当前场景下无需引入更复杂的长连接机制。

从前端组件设计看，系统采用了页面负责组织、组件负责展示、轮询钩子负责调度请求的分层方式。图表组件负责曲线绘制，表格组件负责快照展示，轮询钩子负责定时请求并管理加载状态与错误状态，API 封装负责屏蔽具体接口地址和参数细节。这种结构提升了界面的可维护性。

### 5.2.6 告警规则与事件联动模块设计

告警规则与事件联动模块由规则定义、告警对象和事件记录三部分构成，是系统异常管理逻辑的重要组成部分。

在规则定义方面，系统使用告警规则表保存规则标识、标题、规则来源、字段名、比较运算符、阈值数值、阈值文本、严重级别、启用标记、自动恢复标记和消息模板。默认内置 4 条规则，分别是设备不可用、故障演化高紧迫度、温度过高和采集器异常。规则来源分为指标类和事件类两种，前者在指标写入后评估，后者在事件写入后评估。

在告警生命周期方面，系统使用告警表保存告警对象，并通过唯一索引约束保证同一设备在同一规则下同时只有一条活动告警。告警状态包括打开、已确认、已静默和已恢复等。当同一规则持续触发时，系统会更新已有告警的最后出现时间与事件计数；当条件恢复后，再统一标记为已恢复。后端同时实现了确认与静默的接口逻辑，便于后续扩展页面操作入口。

在事件联动方面，每一次告警打开、恢复、确认和静默动作都会向 `events` 表写入相应事件，这保证了系统中的告警状态变化既是告警对象的一部分，也是可追踪的事件历史的一部分。这样，在仪表盘的事件窗口中可以直接看到异常发生和恢复过程，而不必额外查找外部日志。

## 5.3 数据库详细设计

### 5.3.1 逻辑实体结构设计

根据系统实现，数据库可以分为中心数据库与边端发送队列数据库两部分。中心数据库采用 SQLite 数据库文件形式，主要存放 `devices`、`metrics`、`events`、`alerts` 和 `alert_rules` 五张核心表；边端发送队列数据库主要存放 `outbox` 表。

`devices` 实体描述每台设备的最新快照信息，是面向概览查询的状态实体；`metrics` 实体描述每一次采样明细，是时序历史实体；`events` 实体描述系统行为与异常事件，是审计与追踪实体；`alerts` 实体描述告警对象与其生命周期，是状态管理实体；`alert_rules` 实体描述规则定义，是策略配置实体；`outbox` 实体描述待上传记录，是边端可靠传输实体。

从逻辑结构上看，`metrics` 是整个系统中最丰富的实体，因为它既承载设备动态字段，又承载调度结果和边端反馈，是前后端共享的主数据载体。

### 5.3.2 数据表结构设计

`devices` 表以 `device_id` 为主键，字段包括设备类型、状态、最近时间戳、利用率、温度、功耗、采样间隔、演化分数、相位、字段策略、传输策略、控制分数和更新时间等。其设计目标是支持快速读取每台设备的当前运行状态，因此不会保存长历史。

`metrics` 表采用自增 `id` 作为主键，是系统最核心的数据表。该表除包含 `timestamp`、`time`、`device_id`、`utilization`、`chip_temp_c`、`power_w`、`mem_util_percent` 等基础采样字段外，还包含 `freq_mhz`、`pcie_rx_MBps`、`pcie_tx_MBps`、`correctable_err_s`、`uncorrectable_err_s`、`threads`、`ctx_switch_rate`、`io_util_percent` 等慢线扩展字段；同时还保存 `sample_interval_s`、`evolution_score`、`field_priority_score`、`execution_pressure_score`、`control_score`、`phase`、`field_policy`、`transport_policy`、`outbox_pending`、`outbox_dead`、`ring_backlog`、`overhead_cpu`、`overhead_mem_mb` 等调度与边端反馈字段。可以看出，该表不仅用于监控，也用于评估。

`events` 表采用自增 `id` 主键，主要字段包括时间戳、设备编号、事件类型、严重级别、消息、详情、来源和创建时间。由于事件写入频率低于指标表，因此结构较为轻量，但它承担了异常追踪和告警联动的重要职责。

`alerts` 表采用自增 `id` 主键，保存设备编号、规则键、标题、严重级别、状态、消息、首次发现时间、最近出现时间、确认信息、静默截止时间、关闭时间、事件计数和最近值等字段。`alert_rules` 表则以 `rule_key` 为主键，保存规则定义。边端 `outbox` 表采用自增 `id` 主键，记录类型、序列化负载、状态、尝试次数、下次重试时间、最后错误及创建更新时间等字段。

### 5.3.3 关键字段与约束设计

本系统虽然未在所有表上定义复杂外键，但在关键字段和索引设计上仍然体现了明确约束。

首先，`devices.device_id` 是设备快照唯一标识，保证一台设备在 `devices` 表中只有一条最新记录。其次，`metrics` 表为 `device_id` 和 `id` 建立索引，保证按设备读取最近历史时具备较好查询性能；`events` 表同样为 `device_id` 和 `id` 建立索引，便于按设备筛选事件。再次，`alerts` 表建立了活动告警唯一索引，约束同一设备与同一规则在 `open`、`acknowledged`、`silenced` 状态下只存在一条活动告警，从而避免重复报警风暴。

在数值字段设计上，系统大量使用可空字段。这是因为不同设备并不一定具备完全相同的采样能力，例如部分 CPU 没有显存指标，部分回放数据可能没有功耗上限字段，NPU 实机环境中也可能出现功耗、内存占用等字段暂时不可获取的情况。采用可空设计可以兼容异构来源，并保持模型对不同设备能力的适配性。

在边端 outbox 设计上，`status` 字段用于区分 `pending` 与 `dead` 状态，`attempts` 字段用于限制最大重试次数，`next_retry_at` 字段用于实现到期发送策略。与中心数据库相比，outbox 更关注可恢复性而非业务查询复杂度。

## 5.5 系统接口详细设计

### 5.5.1 外部接口详细设计

考虑到接口路径属于实现级信息，前文未对其逐一展开，本节集中说明系统的对外服务接口。

从对外服务角度看，系统的主要 HTTP 接口可以划分为四组。第一组是系统基础接口，包括 `/health` 健康检查接口，用于判断服务是否在线。第二组是数据查询接口，包括 `/api/devices`、`/api/metrics/realtime`、`/api/metrics/history`、`/api/metrics/compare`、`/api/metrics/logs`、`/api/events`、`/api/dashboard/overview` 和 `/api/experiments/evaluation` 等，它们分别支撑设备快照、单设备历史、多设备对比、日志、事件、概览和实验评估视图。第三组是控制接口，包括 `/api/control/status`、`/api/control/trace`、`/api/control/replay-compare`、`/api/control/live` 和 `/api/control/cancel`，用于控制台页面发起任务与获取状态。第四组是边端接入接口 `/api/ingest`，用于接收 gzip 压缩或普通 JSON 格式的批量记录。

以 `/api/ingest` 为例，请求体中的记录被统一组织为：

```text
{
  "records": [
    {"type": "metric", "payload": {...}},
    {"type": "event", "payload": {...}}
  ]
}
```

后端会根据 `type` 分流处理。这样的接口设计使边端上传协议非常稳定，即使某些字段后续扩展，也不必频繁修改接口路径和基本载荷结构。

## 6.1 系统测试计划

### 6.1.1 测试目的

本项目测试的主要目的是验证系统是否已经形成从设备采样、边端可靠传输、后端接收存储、前端查询展示到实验评估输出的完整闭环。结合系统特点，测试重点包括以下四个方面。

### 6.1.3 测试方法

本项目采用以功能测试和联调测试为主的测试方法，并辅以结果抽样分析。

### 6.3.1 评估指标定义

为了避免只给出零散数字，本节先说明实验报告中几个核心指标的定义方式。

采样点减少率用于衡量自适应采样相对固定频率减少了多少观测次数，其计算公式为：

```text
公式6-1 采样点减少率
R_sample = (N_fixed - N_evolution) / N_fixed × 100%
```

其中，`N_fixed` 表示固定频率模式采样点数量，`N_evolution` 表示故障演化采样模式采样点数量，`R_sample` 越大表示在相同输入下减少的采样次数越多。

冗余率用于衡量系统是否在短时间内重复采集了信息变化较小、观测价值较低的样本。当前评估脚本先计算单点信息增益：

```text
公式6-2 单点信息增益
IG_i = |Δu_i| + 0.35·|ΔT_i| + 0.15·|ΔP_i|
```

其中，`IG_i` 表示第 `i` 个采样点相对前一采样点的信息增益，`Δu_i` 为利用率变化量，`ΔT_i` 为温度变化量，`ΔP_i` 为功耗变化量。随后系统结合采样时间间隔、设备类型、采样相位、字段策略、传输策略以及设备健康状态等条件，判定该点是否属于低信息量重复采样。若记冗余指示变量为 `I_i`，则总体冗余率为：

```text
公式6-3 冗余率
R_red = (1 / N) · Σ I_i × 100%
```

其中，`N` 为总采样点数，`I_i` 取 1 表示该采样点被判定为冗余，取 0 表示非冗余。

延迟指标用于衡量系统从事件发生到采样系统作出观察响应所需时间。当前评估优先使用统一真值事件文件，延迟定义为：

```text
公式6-4 事件响应延迟
L_k = t_resp,k - t_event,k
```

其中，`L_k` 表示第 `k` 个事件的响应延迟，`t_event,k` 表示真值事件发生时间，`t_resp,k` 表示事件发生后系统第一次进入加速响应状态或第一次观测到事件后的时间。当前评估脚本中，加速响应定义为采样间隔较基线下降至少 15%，或者采样相位进入聚焦或恢复状态。

从功能完整性角度看，当前系统已经通过测试证明具备较完整的可运行能力。统一启动可用、关键接口可访问、数据库形成稳定记录、控制台能够发起实验任务、实验目录能够产出报告文件，NPU 实机采集链路也已在 YS-EC588 主板上完成验证，这些事实说明系统已经形成端到端闭环。

从数据链路角度看，本次离线回放评估结束后，边端发送队列中仍保留待发送记录，这与实验未配置远端上传地址的运行方式一致，说明本地缓冲与持久化链路已经生效；数据库中同时存在设备、指标、事件、告警和规则记录，也说明采样、规则联动和持久化过程已经联动发生。

从实验结论角度看，本次 110 s 统一回放对照结果支持以下判断：其一，在固定 5 s 基线下，故障演化采样把总采样点数量从 66 降至 65，同时把冗余率从 34.85% 降至 16.92%，说明系统已经能够在不显著增加观测规模的前提下改善样本有效性；其二，演化模式平均采样间隔略高于固定频率模式，但最小间隔可以收紧到 1.0 s，说明故障演化调度已经具备针对异常窗口的局部加密能力。

从实时性看，演化模式延迟 P50 为 2.219 s，略高于固定频率模式的 2.171 s；延迟 P95 为 3.6381 s，低于固定频率模式的 3.8841 s。该结果说明，在本次轨迹和参数设置下，演化模式对典型事件的平均响应速度与固定频率基本接近，但在较慢响应事件上的尾部控制更好。结合运行日志中出现的聚焦采样、恢复观测以及 NPU 故障窗口下 1 s 级收紧行为，可以认为故障演化调度已经真实参与了采样控制，而不是停留在静态规则层面。

同时，也必须如实指出当前系统的不足。演化模式的 CPU 平均开销高于固定频率模式，说明相位判断、慢线补采和缓冲处理会引入额外计算开销；从分事件延迟结果看，不同异常类型上的收益并不完全一致，部分事件窗口仍存在优化空间。这意味着当前调度参数虽然已经能够体现自适应策略优势，但距离更稳定、更普适的参数配置仍有一定差距。

此外，当前结果仍然属于单轨迹、单参数组的实验结论，虽然比短时样本更完整，但还不足以直接代表所有设备负载场景。若后续要进一步提高实验结论的稳定性与说服力，应当继续扩展回放时长、丰富异常模式、增加多轮重复实验，并对不同设备类别分别开展参数整定。

## 6.5 本章小结

本章围绕系统测试展开，从测试目的、测试用例、测试方法、测试范围、功能验证、结果抽样和结论分析等方面说明了当前系统的真实表现。测试结果表明，系统已经具备较完整的工程可用性，能够输出结构化实验结果，并已完成 YS-EC588 主板上的 NPU 实机采集链路验证；在重新生成的 110 s 回放对照实验中，故障演化采样相对于固定 5 s 模式实现了 1.52% 的采样点减少、17.93 个百分点的冗余率下降和更低的 P95 延迟，同时也表现出一定的 CPU 开销增长。以上结果说明系统已经具备可验证的自适应采样能力，但调度参数和事件响应特性仍有进一步优化空间。以上结论为下一章的总结与展望奠定了基础。

# 第七章 总结与展望

本章对全文工作进行归纳，总结系统已完成的主要成果，并结合测试与实验结果分析现阶段仍存在的不足和后续可完善方向。通过本章可以进一步明确系统的实际完成范围、已经验证的能力以及后续改进重点。

## 7.1 项目的成果与收获

本项目最终完成了一个面向异构算力设备监测场景的故障演化自适应变频采样系统。系统包含设备接入、故障演化调度、边端可靠执行、后端接收存储、前端可视化展示和实验评估链路，已经形成可运行的工程原型。结合前文设计与测试结果，可以将本项目的成果概括为以下几个方面。

第一，完成了异构设备的统一指标建模。系统能够把 CPU、GPU、NPU 适配接口以及回放轨迹输入统一映射到同一套动态指标模型中，从而为调度控制、数据存储和前端展示提供一致的数据基础。NPU 侧已经在亿晟科技 YS-EC588 工业级安卓/鸿蒙兼容主板上完成实机采集链路验证，说明统一模型能够承载边端嵌入式算力设备的实际采样结果。这一成果解决了异构设备字段风格不一致、后续处理链路难以统一的问题。

第二，完成了面向故障演化的自适应采样控制实现。系统根据紧迫度、字段优先级和执行压力三个控制量，动态决定采样相位、字段策略、传输策略和下一次采样间隔。当前实现已经支持聚焦采样、恢复观测、巡航巡检和边端降级四种状态，并能在快线与慢线字段之间进行分层调度。

第三，完成了边端可靠执行链路的工程化落地。系统通过环形缓冲区、SQLite WAL 本地发送队列、批量上传和失败重试机制，使采样主循环与网络上传过程解耦。这一设计增强了系统在网络波动或后端短时不可用情况下的稳定性，也让调度器能够感知执行压力并参与闭环控制。

第四，完成了前后端一体化监控与控制能力。后端已经实现健康检查、数据接收、历史查询、概览统计、事件查询、实验报告读取和控制服务接口；前端已经实现仪表盘与实验控制台两个主要视图，能够同时承担状态观察和任务触发职责。这说明系统已经具备从底层采样到上层页面的端到端实现能力。

第五，完成了可复现实验链路建设。系统支持生成回放轨迹、执行固定频率与演化采样对照、产出结构化报告和图像结果，从而使实验结论具备可复核性。测试结果也表明，系统已经能够自动生成报告并沉淀实验产物。

除了系统成果之外，本项目还带来了较系统的能力收获。在实现过程中，需要同时处理设备采样、调度算法、可靠传输、数据库设计、接口开发、前端展示和实验评估等多个方面的问题。这使得本人进一步加深了对 Python、FastAPI、React、SQLite 和脚本自动化的理解，也更系统地认识了从算法原型到工程闭环的完整实现路径。

## 7.2 项目不足与后期升级

系统已经形成完整原型，但距离更成熟的工程系统仍存在若干不足，后续可以从以下几个方向继续完善。

第一，用户与权限体系有待补充。系统当前面向单操作者场景设计，因此未配置登录、认证、授权、角色隔离和操作审计页面。若后续面向多人协同使用，则需要补充账号体系、接口鉴权和权限分层能力。

第二，告警管理能力仍可继续深化。当前系统已经形成告警中心页面，前后端已支持告警规则展示与维护、活动告警查询、确认、静默、批量处置和趋势统计等功能，能够覆盖告警查看与处置的基本流程。后续可以在现有基础上进一步完善规则编辑交互、告警分级联动、统计分析维度以及与更多运行场景的结合方式，从而提升告警管理的完整性和易用性。

第三，NPU 硬件验证覆盖范围仍需扩大。系统已经在亿晟科技 YS-EC588 工业级安卓/鸿蒙兼容主板上跑通 NPU 实机采集链路，验证了板端 NPU 指标采集、统一模型封装和后续处理流程的可行性。但目前实机验证仍集中在单一型号主板和单一板端环境上，尚未覆盖更多厂商、更多芯片和更多负载类型。后续如果能够接入更多 NPU 设备，将有助于进一步验证系统在更多异构硬件上的通用性。

第四，故障演化调度参数仍有优化空间。虽然当前版本已经通过在线联调把默认上下界收敛到 `1s~6s`、降低了慢线陈旧度权重、放宽了缓冲上传触发条件，并针对 Intel 核显加入了更稳健的异构阈值分支，但这些参数主要是在当前 Windows 主机与当前负载特征下校准得到的。换言之，现有参数能够明显改善轻负载误触发和链路过敏问题，却不代表其在所有 GPU、NPU 或更复杂故障轨迹下都已达到最优。后续可以尝试引入参数自动寻优、更丰富的异常模式和更长时间窗口的多轮实验，以提高演化调度的适应性。

第五，存储与传输架构仍以单机轻量方案为主。系统使用 SQLite 作为中心数据库，也使用 SQLite 作为边端本地发送队列，中心与边端之间通过 HTTP 直接交互。这种方案适合当前系统原型和小规模部署，但若后续面向更大规模设备接入，可以考虑引入消息队列、时序数据库或分布式存储组件，以进一步提升吞吐和扩展性。

第六，评估维度和展示能力仍可继续丰富。当前报告已经包含采样点数、冗余率、延迟、资源开销和部分行为指标，但还可以进一步加入更多异常分类统计、设备分组分析、跨多次实验的报告对比和参数敏感性分析。同时，前端也可以增加报告列表、历史报告切换、图表导出和配置回显等功能。

综合来看，本项目已经完成了本阶段设定的核心目标，即围绕异构算力设备监测场景，设计并实现一个具有故障演化自适应变频采样能力的完整系统原型。后续工作重点将在现有闭环基础上继续增强多设备兼容性、调度有效性、界面完善度和工程可扩展性，使系统逐步向更加成熟、更加稳定和更加实用的方向演进。
