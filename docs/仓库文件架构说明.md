# 仓库文件架构说明

本文档用于梳理当前项目仓库的实际目录结构、各目录职责，以及建议的整理原则。目标不是一次性大规模移动源码，而是在不破坏现有运行链路的前提下，把“源码、文档、实验输入、实验输出、临时文件”分清楚。

## 1. 顶层目录总览

```text
graduation_project/
├─ backend/                 后端 API、数据服务、控制台任务
├─ core/                    采样、调度、采集适配、运行时核心逻辑
├─ demo/                    实验入口脚本、评估脚本、回放生成脚本
├─ docs/                    设计文档、论文草稿、说明文档、架构说明
├─ experiments/             实验输入、实验输出、运行留痕
├─ frontend/                前端页面、图表、接口封装
├─ tools/                   辅助工具脚本、硬件探测工具
├─ .venv/                   本地 Python 虚拟环境
├─ start_system.ps1         一键启动入口
├─ start_system.bat         Windows 批处理启动入口
├─ docker-compose.yml       容器编排配置
├─ requirements.txt         根依赖
└─ prometheus.yml           Prometheus 配置
```

## 2. 当前推荐理解方式

仓库里的内容建议按下面五类理解：

1. 源码区
   `backend/`、`core/`、`frontend/`

2. 实验入口区
   `demo/`

3. 文档区
   `docs/`

4. 数据与结果区
   `experiments/`

5. 环境与工具区
   `.venv/`、`tools/`、根目录启动脚本

## 3. 详细目录架构

### 3.1 `backend/`

后端服务入口，负责数据接收、告警规则、控制台任务、前端静态文件托管。

```text
backend/
└─ app/
   ├─ main.py               FastAPI 入口，注册接口和前端托管
   ├─ data_service.py       设备、指标、事件、告警、规则等数据服务
   ├─ control_service.py    图形控制台后台任务服务
   ├─ database.py           数据库初始化与访问
   ├─ schemas.py            Pydantic 数据模型
   └─ __init__.py
```

### 3.2 `core/`

系统核心实现，是真正的“采样系统引擎”。

```text
core/
├─ adapter/                 设备适配层
│  ├─ cpu/                  CPU 适配器
│  ├─ gpu/                  GPU 适配器
│  ├─ npu/                  NPU 适配器与后端
│  │  └─ backends/          ascend / openharmony_hdc / rockchip_sysfs
│  ├─ replay/               回放轨迹适配器
│  ├─ windows_sensor_reader.py
│  ├─ base_adapter.py
│  └─ __init__.py
├─ buffer/                  环形缓冲区
├─ collector/               采集器封装
├─ model/                   统一设备静态/动态模型
├─ reporter/                Console / Prometheus 等输出
├─ runtime/                 EdgeAgent 运行时编排
├─ sampler/                 单设备采样器
├─ scheduler/               固定频率 / 故障演化调度器
├─ storage/                 SQLite outbox 持久化
└─ uploader/                HTTP 上传器
```

建议理解顺序：

1. `model/`
2. `adapter/`
3. `scheduler/`
4. `sampler/`
5. `runtime/`
6. `storage/` 与 `uploader/`

### 3.3 `frontend/`

前端展示层，当前主要包含监控总览、告警中心、系统控制台。

```text
frontend/
├─ src/
│  ├─ pages/
│  │  ├─ DashboardPage.tsx
│  │  ├─ AlertCenterPage.tsx
│  │  └─ ControlConsolePage.tsx
│  ├─ charts/
│  ├─ components/
│  ├─ api.ts
│  ├─ hooks.ts
│  ├─ types.ts
│  ├─ App.tsx
│  ├─ main.tsx
│  └─ styles.css
├─ package.json
├─ vite.config.ts
└─ index.html
```

### 3.4 `demo/`

实验入口和评估脚本区。这里不是“演示代码”，而是当前项目实验链路的主入口。

```text
demo/
├─ evolution_sampling_experiment.py   真实采集 / 回放对比实验主入口
├─ generate_replay_trace.py           生成标准回放轨迹
├─ evaluate_metrics.py                fixed / evolution 评估脚本
├─ run_midterm_check.ps1              一键联调与验收脚本
├─ mock_ingest_server.py              模拟接收端
└─ data/                              保留的示例数据
```

### 3.5 `docs/`

文档区建议只保留“长期有价值”的材料，不放实验输出。

```text
docs/
├─ 故障演化采样系统设计书.md
├─ 可复现实验链路.md
├─ 系统差距分析.md
├─ 统一字段定义表.md
├─ 论文正文草稿.md
├─ patent_strategy_comparison.md
├─ figures/                           论文/文档配图
└─ 仓库文件架构说明.md
```

### 3.6 `experiments/`

这是当前最容易显得“乱”的目录，因为它同时包含：

1. 实验输入
2. 实验输出
3. 临时文件
4. 历史运行留痕

当前建议按下面方式理解：

```text
experiments/
├─ replay_profiles/       可复现实验输入
│  ├─ heterogeneous_fault_trace.csv
│  ├─ heterogeneous_fault_events.csv
│  ├─ real_npu_trace_20260425.csv
│  └─ real_npu_events_20260425.csv
├─ evaluation/            评估结果
│  └─ latest/             当前最新结果
├─ gui_runs/              前端控制台触发的历史运行结果
├─ live_runs/             实时采集历史结果
├─ midterm_check/         一键验收历史结果
├─ npu_capture/           真实 NPU 原始采集结果
└─ *.csv / *.db / *.log   早期散落产物，建议逐步归档
```

## 4. 目前仓库“乱”的主要原因

### 4.1 源码和实验产物同时出现在工作区

例如：

- `experiments/*.csv`
- `experiments/*.db`
- `tmp_start_system.*.log`

这些都属于运行结果，不属于源码本体。

### 4.2 `experiments/` 根目录历史遗留文件较多

例如：

- `fixed_metrics.csv`
- `evolution_metrics.csv`
- `oh_npu_metrics.csv`
- `quick_verify_fixed.csv`

这些文件本质上都应该归入某个明确的实验子目录，而不是直接平铺在 `experiments/` 根目录。

### 4.3 `latest` 与 `历史运行目录` 并存

这是正常需求，但如果不配合忽略规则和命名规则，就会显得非常拥挤。

## 5. 当前建议的归档规则

不动核心源码的前提下，后续建议统一遵守下面的文件归类规则。

### 5.1 可复现实验输入

统一放到：

```text
experiments/replay_profiles/
```

包括：

- 回放轨迹 `*_trace.csv`
- 事件标注 `*_events.csv`

### 5.2 原始真实采集数据

统一放到：

```text
experiments/npu_capture/
experiments/live_runs/
```

建议：

- “一次性、人工采集”的原始数据放 `npu_capture/`
- “通过系统控制台触发”的运行放 `live_runs/`

### 5.3 评估输出

统一放到：

```text
experiments/evaluation/
```

建议：

- `latest/` 只保留最新一组评估结果
- 历史正式结果按日期或实验名单独建目录

### 5.4 图形控制台任务留痕

统一放到：

```text
experiments/gui_runs/
```

### 5.5 临时验证文件

建议不要长期保留在根目录，统一归到：

```text
experiments/tmp/
```

本轮整理后，历史散落产物已归档到：

```text
experiments/archive/
├─ manual_compare/
├─ openharmony_runs/
├─ quick_verify/
├─ logs/
└─ misc/
```

当前仓库里如果后续继续整理，可以把下面这类文件逐步迁入：

- `experiments/test.csv`
- `experiments/fixed_metrics.csv`
- `experiments/evolution_metrics.csv`
- `experiments/quick_verify_*.csv`

上述历史文件本轮已完成物理整理，不再平铺在 `experiments/` 根目录。

## 7. 当前已完成的低风险整理

本轮整理没有移动核心源码，只做了低风险规范化：

1. 补充仓库架构说明文档
2. 增强 `.gitignore`
3. 把实验生成物、运行目录、临时日志与源码区隔离

## 8. 后续建议

如果要继续做第二阶段整理，建议按下面顺序推进：

1. 清理 `experiments/` 根目录平铺的历史 CSV/DB
2. 给 `experiments/` 增加更明确的 `captures/`、`archive/`、`tmp/`
3. 给 `docs/` 增加首页目录
4. 最后再考虑是否重构 `demo/` 为 `scripts/` 或 `experiments/cli/`

不建议当前立即移动：

- `backend/`
- `core/`
- `frontend/`
- `demo/`

因为这些目录已经被现有启动脚本、导入路径和控制台服务直接依赖。
