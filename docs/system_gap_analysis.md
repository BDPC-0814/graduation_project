# 基于任务书目标的系统差距分析与演进建议

## 0. 先给结论（当前系统成熟度）

你的系统已经完成了课题中最核心的“可运行闭环”雏形：
- 有统一采集接口（`BaseCollector`）与统一动态指标模型（`XPUDynamicMetrics`）；
- 有自适应采样策略（HAVFS）并支持多设备统一调度（`UnifiedScheduler`）；
- 有基础数据输出（CSV）与可观测能力（Prometheus exporter）。

但与任务书“云边端异构算力数据采集系统”目标相比，当前版本仍偏**实验原型**，不足主要在于：
1. **设备覆盖与采集可靠性**：GPU/NPU 不可用时直接回退 0 值，可能造成“假稳定”与误判；
2. **边端轻量化机制不完整**：当前主循环是“串行 sleep + 周期采集”，缺少边端常见的背压控制、缓存淘汰、断点续传；
3. **数据资产能力不足**：仅 CSV 单文件输出，缺少面向状态监测/故障检测的标签化、事件化、分层存储；
4. **前后端系统性不足**：有 Prometheus 输出但缺少完整 API、权限、多租户视图、告警联动；
5. **评估维度可进一步标准化**：已有效率/冗余/延迟评估脚本，但指标定义与实验协议还不够严谨。

## 1. 结合代码现状：目前做到了什么、还有哪些缺口

## 1.1 已满足的任务书能力

### A. 统一模型与接口（已实现）
- 统一采集抽象：`BaseCollector.collect()` 强制 CPU/GPU/NPU 采集器对齐接口。
- 统一动态指标结构：`XPUDynamicMetrics` 统一了 utilization/temperature/power/memory/bandwidth 等字段。
- 这部分与你任务书中“统一采集接口与规范化数据模型”是对齐的。

### B. 自适应变频采样（已实现）
- HAVFS 实现了多维风险计算（A/J/P/D）、风险融合、AIMD 控制、滞回状态机与高风险缓冲。
- 对单设备与多设备（每设备独立 HAVFS，再取全局最小采样间隔）都可运行。

### C. 原型链路（已实现）
- “采集 -> 调度 -> 输出”闭环完整。
- 输出通道有两条：控制台、Prometheus（可接 Grafana）。
- 同时有离线评估脚本（固定频率 vs HAVFS）。

## 1.2 与任务书目标的关键差距

### A. 云边端定位：当前更像“单节点实验”，不是“边端代理系统”
- 当前 `demo/havfs_experiment.py` 是单进程脚本，缺少边端 daemon 化能力（守护进程、服务恢复、热更新配置）。
- 未体现“云边端协同协议”：边端采集后如何上送、重试、压缩、批量传输、断网缓存。

### B. 异构采集覆盖度仍有限
- GPU 仅 NVIDIA NVML + Windows Intel 兜底；NPU 当前仅尝试 Ascend `npu-smi` 文本解析。
- 不支持多 GPU/NPU 卡枚举、拓扑（NUMA/PCIe）信息、设备健康状态码（如驱动错误、ECC）。

### C. 数据语义不足以直接支撑故障检测
- 当前核心输出是时序指标与风险分；缺少事件语义（阈值越界事件、突变事件、设备失联事件）。
- 缺少“标签体系”：站点、设备角色、业务负载类型、算子类型、模型版本等上下文标签。

### D. 可视化与后端能力仍不完整
- 有 exporter 无后端 domain API（查询、聚合、统计、告警确认、规则管理）。
- 无前端应用（仪表盘、设备详情页、历史回放、风险分解解释）。

### E. 评估方法尚未形成可复现实验协议
- 现有评估脚本有价值，但冗余率、实时性定义还可更严谨（例如按事件窗口定义“响应时延P95”）。

## 2. 对你提出的四个问题的建议

## 2.1 问题1：边端侧如何采集不同算力设备指标，并兼顾实时性和轻量化？你当前系统是否满足？

### 建议的边端采集架构（推荐）

建议在边端实现“三层结构”：
1. **Adapter 层（设备适配）**
   - CPU：`psutil` + `/proc/stat`（Linux）
   - GPU：NVML/ROCm SMI/Intel Level Zero
   - NPU：Ascend CANN API（优先 API，少用命令行解析）
2. **Sampler 层（变频采样）**
   - 每设备独立 HAVFS 状态；
   - 关键指标（util/temp/power）可高优先级采样，非关键指标低频采样。
3. **Buffer + Uploader 层（边端可靠上送）**
   - 内存环形缓冲 + 本地 WAL（磁盘落盘）；
   - 批量压缩上送（gRPC/HTTP），失败重试与指数退避。

### 实时性与轻量化的关键机制
- **实时性**：
  - 采集与上送解耦（两个线程池或协程）；
  - 调度决策与采集执行分离，避免网络抖动影响采样。
- **轻量化**：
  - 固定内存预算（如 50MB）+ 环形队列；
  - 字段分级采样（关键字段必采，扩展字段按需采）；
  - 对稳定设备启用“变化阈值上报”（delta encoding）。

### 你当前系统是否满足
- **部分满足**：已有统一接口 + 自适应采样，这是核心优势；
- **未完全满足**：边端可靠传输、缓存治理、资源预算控制尚缺失，因此还没达到“工程级边端代理”的成熟度。

## 2.2 问题2：要支撑状态监测与故障检测，系统应输出什么？如何存储？

### 建议输出的三类数据

1. **Raw Metrics（原始时序）**
   - `timestamp, device_id, util, temp, power, mem, bw`
   - 用于回溯与离线训练。

2. **Derived Features（派生特征）**
   - `risk_score, trend_slope, jump_score, drift_score, state_label`
   - 为故障检测模型提供输入。

3. **Events（事件流）**
   - `threshold_breach`, `rapid_jump`, `collector_unavailable`, `device_offline`
   - 每个事件包含：开始/结束时间、严重级别、根因字段。

### 建议的存储分层

- **边端短期存储**（1~3天）：
  - SQLite/Parquet（压缩、低依赖）
  - 用于断网缓存和近实时回放。

- **云侧长期存储**：
  - 时序库（VictoriaMetrics/InfluxDB/TimescaleDB）存 raw + derived；
  - 对象存储（MinIO/S3）存归档文件（Parquet）；
  - 事件库（PostgreSQL）存告警闭环与工单关联。

### 当前系统缺口
- 目前只落 CSV，缺索引、压缩、TTL、分区策略，不利于规模化查询与模型训练。

## 2.3 问题3：要做完整前后端和更丰富可视化，后续怎么实现？

### 推荐演进路线（4阶段）

1. **Phase-1：后端服务化**
   - 把 `demo` 脚本拆成服务：采集服务、调度服务、查询 API；
   - 提供 REST API：
     - `/devices`
     - `/metrics/realtime`
     - `/metrics/history`
     - `/events`
     - `/scheduler/config`

2. **Phase-2：前端可视化**
   - 技术栈：Vue/React + ECharts；
   - 页面：
     - 全局大盘（设备在线率、风险热力图、采样频率分布）
     - 单设备详情（util/temp/power 与 interval/risk 双轴图）
     - 事件中心（按站点/设备过滤）

3. **Phase-3：告警与解释性**
   - 风险分解可视化：A/J/P/D 四分量堆叠图；
   - 告警规则引擎（阈值 + 连续窗口条件）；
   - 告警确认、静默、升级策略。

4. **Phase-4：故障检测联动**
   - 接入异常检测模型（Isolation Forest/LSTM-AE）；
   - 以事件形式回写系统，形成“采集-分析-告警”闭环。

### 你当前系统可复用的基础
- Prometheus reporter 已可直接接 Grafana 做第一版大盘。
- HAVFS 风险与状态标签已具备良好的“可解释可视化”基础。

## 2.4 问题4：如何更好评估采集效率、冗余率、实时性并持续优化参数？

### 建议建立“统一评估协议”（非常关键）

#### A. 采集效率（Efficiency）
- 指标：
  - `points_per_min`（单位时间采样点）
  - `bytes_per_min`（单位时间写入量）
  - `cost_per_signal`（每个有效事件的采集成本）
- 对比：固定频率 vs HAVFS，在同一负载回放集上比较。

#### B. 数据冗余率（Redundancy）
- 当前“变化<1%”可保留，但建议补充：
  - `duplicate_window_ratio`：窗口内方差低于阈值的比例；
  - `information_gain`：采样前后熵增或变化点覆盖率。

#### C. 实时性（Timeliness）
- 用事件驱动定义更严谨：
  - 负载突增事件 `E_start`；
  - 系统进入高频阈值 `T_highfreq`；
  - 定义 `latency = T_highfreq - E_start`；
  - 统计 P50/P95/P99，而非仅均值。

#### D. 系统开销（Overhead）
- agent CPU%、RSS、上下文切换、I/O 吞吐；
- 边端网络上送带宽与失败重试次数。

### 参数优化建议（HAVFS）
- 网格/贝叶斯优化参数：
  - `w1~w4, enter_high, exit_high, t_min, t_max`
- 多目标优化：
  - 最小化冗余率 + 开销
  - 约束实时性（P95 延迟 < 1s）
- 用“典型工况回放集”做离线寻优，再线上灰度验证。
